Why does this happen? ▶

AI agents optimize locally — they generate code that works for the immediate task but drifts from the overall architecture. Without shared contracts, parallel agents create incompatible interfaces. Without upstream specs to check against, there's no way to detect when the code no longer matches what was intended.

The missing piece isn't smarter AI — it's structured specifications that act as contracts between humans and agents, and between agents and other agents.

The Solution: A Contract Stack

VibeLoom generates a tiered stack of structured specs. Each tier constrains the next. Upstream specs serve as evaluations for downstream work.

How It Works

A single command — /vibeloom — guides you through the entire lifecycle: from initial idea to production code, and through every change after that.

1. Start with Intent ▶

Run /vibeloom init to scaffold your project. Describe what you want to build in plain language — or let the Agent interview you. The result is intent.md, a structured capture of your vision.

Already have code? /vibeloom import analyzes your existing codebase and generates specs that describe what it currently does.

2. Generate Product Specs ▶

After approving the intent, the Agent generates three product-level specs as a batch:

  • PRD — structured requirements with priorities and acceptance criteria
  • User Story Map — epics and stories that reveal user workflows
  • Domain Model — DDD-style entities, relationships, and invariants

You review all three together. Edit any of them — the Agent checks consistency across the batch and flags contradictions.

3. Generate Technical Specs ▶

Once product specs are approved, the Agent selects a profile (Lite or Full) based on domain complexity, then generates the architecture/design spec: tech stack, API design, data model, security, deployment, and module decomposition.

For Full profile projects, each module gets its own spec with explicit interface contracts — defining what it exports, what it imports, and its boundaries.

4. Generate Code & Tests ▶

With all specs approved, /vibeloom generate code produces the implementation. For Full profile, generation is per-module — each module fits in a single Agent context window.

/vibeloom generate tests derives test scenarios from user stories, domain invariant tests from the domain model, and contract tests from interface specs.

5. Evolve with Confidence ▶

/vibeloom develop "add CSV export" — describe your change in natural language. The Agent maps it to affected specs, proposes spec changes first, then generates code. You choose whether to review specs and code separately or as a batch.

Manual spec edits? /vibeloom reconcile runs a bounded consistency check: one upstream pass, one downstream pass, one final validation. No infinite loops.

Two Profiles for Every Scale

VibeLoom adapts to your project's complexity. The Agent recommends a profile based on domain model analysis; you have the final say.

Lite

Single domain, single agent
  • Up to ~15 entities, one bounded context
  • USM inlined in PRD (fewer files)
  • No module decomposition
  • 2 approval gates
  • Best for MVPs, tools, internal apps

Full

Multiple domains, parallel agents
  • Multiple bounded contexts
  • Separate USM with full story structure
  • Modules with interface contracts
  • 3 approval gates
  • Best for platforms, SaaS, team projects
Profile selection criteria ▶

Use Full when ANY of these are true:

  • The domain model has natural subdomain boundaries
  • Multiple agents or developers will work in parallel
  • The codebase will exceed ~50 files or ~10K lines
  • Independent deployment of subsystems is needed

Otherwise, use Lite. You can upgrade from Lite to Full later if the project grows.

Specs as Evals

Specifications aren't just documentation — they're verification contracts. Three tiers of evaluation ensure everything stays consistent.

Tier Type What it checks Blocking?
Tier 1 Structural IDs valid, cross-refs resolve, required sections present, module directories match spec Yes — must pass to proceed
Tier 2 Semantic Coverage gaps, contradictions, orphan entities, NFRs not addressed No — warnings, human decides
Tier 3 Behavioral Test scenarios from stories, invariant tests from domain model, contract tests Separate step (generate tests)
How evals work in practice ▶

Every artifact uses rigid IDs (e.g., PRD-001, DM-BC1-E05, USM-E01-S03) that enable mechanical cross-referencing. When you run /vibeloom eval, the Agent reads all artifacts and checks that every reference resolves, every requirement has covering stories, every entity has an owning module.

Tier 1 evals run automatically after every generation or edit. Tier 2 runs before you approve. If anything fails, you see exactly what's wrong and what to fix.

Built for Multi-Agent Development

Modules aren't just code organization — they're agent boundaries. Each module fits in a context window and can be worked on independently.

Mechanism What it enables
Module decomposition Each agent works within one module's scope, loading only its spec + interfaces
Interface contracts Typed exports/imports prevent agents from creating incompatible APIs
Dependency DAG Enforces build order and prevents circular dependencies
Shared types with ownership Only the owning module can change a type; others adapt
Context loading protocol 60% code, 30% specs, 10% system prompt — prevents context overflow
How context loading works ▶

When an agent generates code for a module, it loads:

  • Verbatim: module spec, module AGENTS.md, interface contracts
  • Summarized: domain model (own bounded context only), root spec overview
  • Not loaded: other modules' code, upstream prose specs

Specs have recommended maximum lengths (module spec ≤ 3K tokens). Exceeding the limit signals the decomposition is too coarse.
