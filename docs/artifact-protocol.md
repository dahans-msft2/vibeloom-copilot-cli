# Artifact Protocol

This document defines the exact normative shape of the VibeLoom artifacts used by the Codex package.

It assumes the canonical layer contract from [vibeloom-methodology.md](vibeloom-methodology.md); refer there for repo-layer authority and loading boundaries.

This document focuses on artifact shape, metadata, and cross-reference rules rather than re-explaining repo layering or restating every methodology-wide policy.

## Common Frontmatter

Canonical artifacts must include:

| Field | Type | Notes |
| --- | --- | --- |
| `artifact_id` | string | Stable file-level identifier |
| `artifact_type` | enum | `constitution`, `intent`, `prd`, `usm`, `dm`, `spec` |
| `status` | enum | `draft`, `approved`, `stale`, `superseded` |
| `owner` | string | Human or logical owner |
| `approved_by` | string or empty | Human approver |
| `last_reviewed` | date or placeholder | Last approval date |
| `version` | integer | Monotonic version number |
| `derived_from` | list | Inputs used to create the current version |
| `depends_on` | list | Approved upstream artifacts |

Optional fields:
- `profile`: concrete project specs; not required for methodology-package meta-specs
- `module_id`
- `bounded_context`

## Item Kinds By Artifact

### `constitution.md`

Required item kinds:
- lifecycle states
- ID grammar definitions
- change classes
- traceability rules
- context-loading rules
- universal quality defaults

Allowed references:
- artifact types
- ID prefixes

### `intent.md`

Required item kinds:
- primary users
- core capabilities
- constraints and preferences
- non-functional expectations
- optional reconciled capability index using `CAP-*`

Allowed references:
- none required upstream

Rules:
- Draft intent is prose-first and may omit stable item IDs.
- Reconciliation may add optional `CAP-*` capability IDs when downstream item-level trace needs explicit intent references.

### `prd.md`

Required item kinds:
- `USR-*`
- `GOAL-*`
- `METRIC-*`
- `PRD-FR-*`
- `NFR-*`
- scope boundaries
- risks

Allowed references:
- reconciled `CAP-*` capability IDs when item-level intent trace is claimed

### `usm.md`

Required item kinds:
- `EPIC-*`
- `STORY-*`
- `AC-*`
- story dependencies
- cross-cutting stories where needed

Allowed references:
- `USR-*`
- `PRD-FR-*`
- `ENT-*`

### `dm.md`

Required item kinds:
- `BC-*`
- `ENT-*`
- `INV-*`
- relationships
- glossary

Allowed references:
- `STORY-*`
- `PRD-FR-*`
- `NFR-*` when invariants or policies are driven by non-functional requirements

### `spec.md`

Required item kinds:
- profile declaration for concrete governed repo specs, or an explicit meta-spec exception when the package spec describes multiple supported profiles
- module responsibilities
- module ownership rules
- interface ownership rules
- technical policies
- context-loading algorithm
- reconcile behavior
- bugfix behavior
- projection definitions

Allowed references:
- `PRD-FR-*`
- `NFR-*`
- `STORY-*`
- `ENT-*`
- `INV-*`
- `MOD-*`
- `API-*`

Rules:
- Concrete governed project `spec.md` files must declare one selected `lite` or `full` profile and align their ownership and decomposition rules to it.
- A methodology-package `spec.md` may act as a meta-spec that documents both supported profiles and generated-repo expectations. When it does, it must say so explicitly and may omit a selected-profile frontmatter field.

## Cross-Reference Rules

| From | Must reference |
| --- | --- |
| `prd` | reconciled `CAP-*` capabilities when item-level intent trace is claimed |
| `usm` | `prd` requirements and `usr` personas |
| `dm` | `usm` stories and `prd` requirements |
| `spec` | `prd`, `usm`, and `dm` items |
| `plan` | touched canonical items and validation IDs |
| `AGENTS` | current scope contracts only |

## Derived Artifacts

### `AGENTS.md`

- derived from canonical contracts and the active context slice
- non-canonical
- regenerable
- may contain task-specific rules, commands, and scope reminders
- must not introduce new semantic truth

### `plan.md`

- derived from canonical contracts for one change
- non-canonical
- regenerable
- must include touched IDs, tasks, validations, and stale implications
- must not redefine upstream requirements, stories, entities, or invariants

## Profile Rules

- `lite` requires `constitution`, `intent`, `prd`, `usm`, `dm`, and `spec`.
- `full` requires all of the above plus module specs and explicit interface ownership.
- No profile may omit `usm.md` or `dm.md`.

## Authority Rules

- Canonical artifacts are approved by humans.
- Derived artifacts may be regenerated by agents.
- Approved upstream truth cannot be silently rewritten by downstream edits or code.

## Projection Rules

The methodology allows only:
- trace index
- dependency/stale graph
- interface/schema manifests

Any proposal to add another durable projection is a methodology change.
