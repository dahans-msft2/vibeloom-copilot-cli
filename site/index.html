Why Now

Spec-driven and contract-driven workflows are getting real attention

More teams are looking for spec-first, spec-driven, contract-first, and contract-driven ways to get better results from AI-assisted development without relying on prompt-only workflows.

Spec-first

Technical specs, implementation-oriented designs, or execution plans are written before implementation starts. The spec exists up front instead of emerging after the code.

Contract-first

Requirements, acceptance criteria, interfaces, invariants, and policies are defined before code generation. Contracts operate at a broader level than technical specs alone.

Spec-driven

Those technical specs keep steering the workflow after planning. They inform implementation, reviews, and change management instead of becoming a stale document.

Contract-driven

Those requirements, acceptance criteria, interfaces, invariants, and policies remain active later as eval inputs, approval gates, and reconciliation checks.

The Solution

Structured specs that
act as contracts

VibeLoom generates a tiered stack of specifications. Each tier constrains the next. Upstream specs serve as evaluations for downstream work.

Contract Stack

Constitution → Intent → PRD → USM → Domain Model → Spec → Code. Each tier is verified against its upstream contracts.

Domain Model Anchor

DDD-style domain model is the semantic core. It captures user value independently of technical decisions — the most stable layer.

Multi-Agent Ready

Modules derived from bounded contexts. Each fits one context window. Interface contracts prevent incompatible APIs between parallel agents.

Specs as Evals

Three-tier evaluation: structural checks (blocking), semantic coverage analysis (warnings), and test generation from specs (on-demand).

Bidirectional Consistency

Edit any spec — upstream and downstream are checked automatically. Bounded reconciliation: one up-pass, one down-pass, no infinite loops.

Human Governed

Three approval gates keep governance explicit: intent, product, and spec. Agents generate, you verify. Four lifecycle states (draft, approved, stale, superseded) keep governance explicit.

One command to rule them all

Invoke $vibeloom for state-aware triage, then use /vibeloom <action> <target> <context> when you want an explicit command.

/vibeloom init Scaffold new project
/vibeloom import Spec existing codebase
/vibeloom generate <selector> Generate next artifact
/vibeloom approve <target> [context] Approve after review
/vibeloom develop Incremental changes
/vibeloom fix <repro-or-bug> Fix a steady-state defect
/vibeloom eval <target> [context] Run consistency checks
/vibeloom review <target> [context] Walk through one artifact or module
/vibeloom reconcile Fix after manual edits
/vibeloom status See project state
/vibeloom surface <product-first|code-first> Set the current session surface
/vibeloom help ... Guidance for topics or one command
