Foundation

Core Thesis

Five principles that underpin everything VibeLoom does.

1. Prompts are not contracts▶

Prompt-first generation is insufficient for long-lived systems. A natural-language prompt is vague by nature and cannot serve as a verifiable contract. Multiple semantic layers are missing between "build me a scheduling app" and the code that implements it: requirements, user stories, domain model, architecture decisions.

2. AI makes specs economically viable again▶

Historically, teams were lax about maintaining high-quality specifications — the overhead was too high. With AI agents, generating and maintaining structured specs is cheap. This doesn't mean returning to 200-page requirements documents. It means concise, structured specs that humans can scan in minutes, verify, and spot-edit.

3. Upstream specs must be evals▶

Every derived artifact and every implementation unit is checked against its upstream contracts. This is the enforcement mechanism — not aspiration, but concrete evaluations with defined pass/fail criteria and blocking behavior.

4. Modules enable multi-agent development▶

Breaking the application into modules scoped to bounded contexts enables parallel agent work, controls context window usage, and provides clear ownership boundaries. Each module fits in one agent's context window. Interface contracts prevent incompatible APIs between agents working in parallel.

5. Workflow semantics and domain semantics must stay separate▶

The User Story Map (USM) captures workflows, user value, and acceptance criteria. The Domain Model (DM) captures entities, relationships, and invariants. Both are mandatory in every profile. Merging them hides workflow mistakes inside semantic models or buries domain rules inside user stories. Keeping them separate ensures each layer can be reviewed, evaluated, and evolved independently.

The Contract Stack

Seven tiers from foundational rules to running code. Each constrains the next. Upstream specs serve as evals for downstream work.

Why rigid IDs matter▶

Every item in every artifact gets a rigid, machine-parseable ID using 17 standardized prefixes (PRD-FR-, STORY-, ENT-, INV-, MOD-, IFACE-, etc.). This enables Tier 1 structural evals to be fully mechanical: the Agent can verify that every ENT-005 referenced in a module spec actually exists in dm.md. Without rigid IDs, consistency checking degrades to "does this look right?" — which is unreliable.

Why the domain model is the semantic anchor▶

dm.md defines entities, relationships, and invariants as seen by system users — not internal technical details. It captures user value independently of implementation choices. The domain model is the most stable layer: UIs change, APIs change, databases change, but "a Customer has Orders which contain LineItems" rarely does.

Scaling

Lite vs Full Profiles

VibeLoom adapts to project complexity. The Agent recommends a profile after analyzing the domain model; you have the final say.

Lite

Single domain, single agent
  • ✓ Up to ~15 entities, one bounded context
  • ✓ Separate USM + DM (always mandatory)
  • ✓ Shallow module decomposition
  • ✓ 3 approval gates (intent, product, spec)
  • ✓ Best for MVPs, tools, internal apps

Full

Multiple domains, parallel agents
  • ✓ Multiple bounded contexts
  • ✓ Module specs with interface contracts + DAG
  • ✓ Explicit interface ownership rules
  • ✓ 3 approval gates (intent, product, spec)
  • ✓ Best for platforms, SaaS, team projects
Selection heuristics▶

Use Full when ANY of these are true:

  • More than one bounded context is clearly named
  • One module cannot own the full write surface without ambiguity
  • Interfaces between semantic areas need stable contracts
  • Multiple agents or developers will work in parallel

Otherwise, use Lite. You can upgrade from Lite to Full later.

Quality

Eval Framework

Specifications aren't documentation — they're verification contracts. Three tiers of evaluation keep everything consistent.

TierTypeWhat it checksBlocking?
Tier 1StructuralIDs valid, cross-refs resolve, required sections present, module dirs match specYes
Tier 2SemanticCoverage gaps, contradictions between tiers, orphan entities, NFRs not addressedWarnings
Tier 3BehavioralTest scenarios from stories, invariant tests from dm.md, contract testsSeparate
Tier 1: Structural checks (10 checks, blocking)▶
  1. Metadata completeness — required frontmatter fields present with valid values
  2. Artifact authority — canonical vs derived status correctly assigned
  3. ID grammar compliance — all items use the 17 defined prefixes (PRD-FR-, STORY-, ENT-, etc.)
  4. Reference integrity — every cross-file ID reference resolves to an existing item
  5. Lifecycle correctness — only valid lifecycle states used (draft, approved, stale, superseded)
  6. Profile correctness — lite or full only; USM and DM always mandatory
  7. Traceability completeness — intent → PRD → USM → DM → spec → test chain intact
  8. Projection budget — only 3 durable projections allowed
  9. Module and interface ownership — every module has clear ownership (Full profile)
  10. Stale edge validity — stale markers have explicit dependency-driven justification
Tier 2: Semantic checks (10 checks, warnings)▶
  • Requirements ↔ Stories coverage
  • Stories ↔ Entities coverage
  • Orphan detection (entities with no stories)
  • Contradiction detection between tiers
  • Module ↔ Entity ownership (one owner per entity)
  • Interface contract completeness (imports match exports)
  • Dependency DAG validation (no cycles)
  • NFR coverage in spec.md
  • Story-to-API traceability
  • Invariant preservation in API design
Tier 3: Behavioral (test generation, separate step)▶

Triggered via /vibeloom generate tests:

  • Scenario descriptions from usm.md stories
  • Domain invariant tests from dm.md
  • Interface contract tests from module specs (Full)
Multi-Agent

Module Interface Contracts

Modules aren't just code organization — they're agent boundaries. Each fits in one context window with typed interfaces.

Interface contract example▶
## Interface: mod-orders

### Exports
- API-01: createOrder(items: CartItem[], customer: CustomerId) → OrderId
- EVT-01: OrderPlaced { orderId, customerId, total, timestamp }

### Imports
- From mod-inventory: checkAvailability(sku: string) → AvailabilityResult
- From mod-payments: chargePayment(customerId, amount) → PaymentResult
Dependency rules & shared types▶
  • Dependency graph must be a DAG (no cycles)
  • New cross-module dependencies require spec.md amendment (human-approved)
  • Shared types have an owner module — only the owner can change the definition

When an interface changes: eval identifies downstream modules → marks stale → specs update → contract tests regenerate.

Context loading protocol▶

Each agent task gets a context envelope:

  • Verbatim: module spec, AGENTS.md, interface contracts
  • Summarized: dm.md (own BC), root spec overview
  • Not loaded: other modules' code, upstream prose

Budget: 60% code, 30% specs, 10% system prompt. Module spec ≤ 3K tokens — exceeding signals decomposition is too coarse.

Command Reference

/vibeloom with no arguments detects project state and suggests the next action.

/vibeloom init Scaffold new project
/vibeloom import Spec existing codebase
/vibeloom generate Generate next artifact or code
/vibeloom approve Approve drafts after eval
/vibeloom develop Incremental change (specs first)
/vibeloom eval Run consistency checks
/vibeloom review Interactive walkthrough
/vibeloom reconcile Fix after manual edits
/vibeloom status Show project state
/vibeloom help Guidance & docs
Key workflow: /vibeloom develop▶
  1. Describe a change: /vibeloom develop "add CSV export"
  2. Agent maps to affected specs (stories, entities, modules)
  3. Agent proposes spec changes first (shows diffs)
  4. You choose: review separately, or batch spec+code approval
  5. Agent runs bounded reconciliation if upstream affected
  6. Agent generates code scoped to affected modules
  7. Agent runs evals on the result

Specs always lead. Code is always a derivative of approved specifications.

Reconciliation: bounded, not infinite▶

After manual edits: 1 up-pass + 1 down-pass + 1 validation. No infinite loops.

Reconciliation is asymmetric: approved upstream contracts define intended semantics. Downstream drift produces proposals, not silent rewrites. The agent proposes a direction (amend upstream or fix downstream), and humans choose.
