codæ

Contract-driven agentic engineering for dark-factory AI coding.

The end-state of AI coding is not autocomplete or faster pull requests. It is a dark factory: contract in, production system out. Humans govern intent and constraints. Agents derive, generate, verify, repair, and regenerate the implementation. By early 2026 the pattern is shipping in pioneering organizations.

Today, the factory doesn't stay dark. Agents produce code at machine speed but cannot preserve meaning across long-running systems. The failure modes have names: AI slop, semantic drift, comprehension debt. The blocker is coherence. codæ proposes the missing control surface: a human-mendable, machine-checkable contract — mutually-derived specs tied by a graph.

§1 — The destinationSoftware wants a dark factory.

AI coding is usually described as assistance: autocomplete, chat, pair programming, faster pull requests. That is the transitional form. The destination is production-system synthesis — an approved contract goes in, a production system comes out.

Contract in. Production system out.

— the dark-factory target

A dark factory does not mean humans disappear. It means humans leave the implementation floor. They govern the contract — intent, product behavior, domain rules, architectural constraints, operational requirements, tradeoffs. Agents derive, build, test, configure, check, diagnose, regenerate.

The dark-factory loop. Humans maintain the contract. Agents operate the factory. Generated implementation is an output, not the primary maintenance surface. Drift returns to the contract — never to the factory floor.

The pattern is already shipping. In February 2026, Spotify's co-CEO confirmed the company's best engineers hadn't written a line of code since December — instead merging hundreds of agent-authored PRs per month through Spotify's internal coding-agent platform, Honk.16 Two weeks later, BCG Platinion's Dark Software Factory report named the threshold: "as few as three engineers can run a software factory where humans no longer write code… The moat is not the code. The moat is the specification and the scenario architecture that validates it."11 Demis Hassabis describes the same shift from the model side in his 2026 YC talk: research-grade autonomy at lengthening horizons.23

"You have to be in charge of the aesthetics, the judgment, the taste, and the oversight. People have to be in charge of this spec, this plan."

— Andrej Karpathy, "From Vibe Coding to Agentic Engineering," Sequoia AI Ascent 202525

The economic case writes itself. The industry-promised 10×–100× productivity gain lives in one place: the dark factory. The moment humans must step back onto the implementation floor, the gain collapses into inspection of machine-volume output. Reading 100,000 lines to safely change 100 isn't a 100× operation — it's barely 1×.

codæ commits to dark-factory coding as a multi-year trajectory, not a v0.3 promise. Today's agents are not yet trustworthy enough to leave alone with the code. The destination is real; the rest of this manifesto is the path.

§2 — The contractThe control surface that holds the factory together.

A prompt cannot govern a dark factory. A codebase is too large to be the human control surface. A requirements document is too weak if agents can ignore it. The missing object is a contract — authoritative enough to govern generation, structured enough for agents to consume, and small enough for humans to mend.

Definition

A codæ contract is the authoritative control surface of an agentic engineering system: human-mendable, agent-legible, machine-checkable, traceable end-to-end from intent to running code.

A contract is not documentation, a prompt, a requirements file, or annotations on generated code. None of those govern. Only a contract does.

A contract has four parts. Specs are the atoms. The graph is the structure. Obligations and checks make it load-bearing.

Specs

The atoms. Typed artifacts each carrying one obligation: a requirement, a capability, a flow, an interface, an invariant, a decision, an acceptance criterion, an operational rule.

Graph

The structure. Typed edges connecting specs — derivation, refinement, satisfaction, conflict, traceability.

Obligations

The force. What every generated artifact must satisfy to count as a faithful realization of the contract.

Checks

The enforcement. Structural, mechanical, and semantic verifications that detect contract violations before they enter the working tree.

The contract inherits two foundational lineages. Its domain layer — bounded contexts, ubiquitous language, aggregates, invariants — extends Eric Evans's Domain-Driven Design vocabulary30: the model humans agree on is the model the code is generated to satisfy. Its form — structured artifacts with typed obligations and a graph of derivations — extends the Domain-Specific Languages tradition traced by Fowler and Parsons29: the canonical answer to "how do you write a specification more rigorous than prose but cheaper than first-order logic?" A codæ contract is a multi-tier internal DSL, with each tier (intent, product, UX, system, runtime) a small, opinionated language for one aspect of what the system must be — designed for human authors and machine consumers at once.

After the contract exists, the primary noun is contract, not specs. Specs are building blocks; the contract is what holds the factory together.

§3 — The paradigmcodæ is contract-driven agentic engineering.

codæ is the discipline of building production systems through intelligently orchestrated coding agents governed by a contract. The contract is not documentation around the code — it is the source of truth the code is generated to satisfy.

codæ makes dark-factory coding possible by moving human control from code to contract.

— codæ thesis

Agents do not merely receive a task. They inherit a contract, derive missing artifacts from it, implement against it, verify outputs against it, and report unresolved contradictions back into it. Humans don't repair the factory by spelunking through generated implementation; they mend the contract and let the factory regenerate.

The pattern already takes primitive shape inside today's agents. Anthropic's Claude Code best-practices describes the entry-level case: "Claude doesn't really have memory. The main way we share state across sessions or across our team is this CLAUDE.md file."24 A single markdown file is the proto-contract. codæ is the structured generalization — not one file but a tiered Contract Graph; not implicit guidance but typed obligations and checks.

One contract

The maintained source of truth. Generated code, tests, infrastructure, and traces are downstream artifacts subordinate to it.

Many specs

Atomic obligations expressing requirements, domain meaning, interfaces, behaviors, constraints, and decisions at the right level of abstraction.

Many agents

Specialized roles — derive, implement, test, inspect, repair, refactor, deploy, observe, explain — orchestrated against the same contract.

Many checks

Structural, mechanical, and semantic verifications that continuously test whether generated artifacts satisfy the contract.

From spec-driven to contract-driven

codæ is adjacent to spec-driven development but a step beyond it. The 2026 SDD taxonomy19 places existing approaches at three rigor levels: spec-first (specs guide, then drift), spec-anchored (specs and code co-evolve with enforcement), spec-as-source (specs alone are edited; code is regenerated). All three are progress over prompt-only generation. AWS Kiro, GitHub Spec Kit, and BMAD live in this band.

codæ is the next level: contract-driven. Not one spec per file or feature, but a multi-tier, mutually-derived, graph-tied, drift-detecting contract that governs the whole lifecycle. Spec-driven asks how to make specs better inputs to generation. Contract-driven asks how to make a contract the durable control surface of the lifecycle.

The academic literature is arriving at the same destination by another route. Margaret-Anne Storey — Canada Research Chair in Human and Social Aspects of Software Engineering — proposes a Triple Debt Model for AI-era software health9: technical debt in code, cognitive debt in developers' minds, and intent debt — the absence of externalized rationale that developers and AI agents need to work safely with code. The codæ contract is that externalized intent. Storey names the debt that accumulates without a contract; codæ is the maintained surface that pays it down.

§4 — The blockerCoherence fails, and local fixes can't restore it.

The obstacle to dark-factory AI coding is not syntax, boilerplate, or local generation — agents handle bounded tasks well. The gating constraint is coherence: preserving intent, architecture, domain meaning, constraints, and behavior across long-running, multi-component, multi-agent work.

When coherence fails, the symptoms have names:

  • Semantic drift — outputs progressively diverge from task intent while remaining plausible and syntactically valid.
  • AI slop6 — code that looks reasonable, passes review-by-glance, and accumulates faster than reviewers can absorb.
  • Comprehension debt4 — the codebase appears clean, but no human or incoming agent understands what it does or why.

These are evidence that the current factory has no durable control surface. Nicole Forsgren — DORA-research lead, co-author of Accelerate — frames the team-level corollary in her 2026 Pragmatic Engineer talk: high-performing teams systematize what was previously tacit context.21

SlopCodeBench7 makes it mechanical: 20 problems × 93 checkpoints × 11 models, instrumented for degradation under evolving requirements. No agent solves a whole problem end-to-end. Agent code runs 2.2× more verbose than open-source Python.

The same pattern appears in live code. Liu et al.10 tracked 302.6k AI-authored commits across 6,299 repositories; of 484,366 introduced issues, 22.7% survive. Baltes, Cheong, and Treude6 name the social cost: gains for one developer become review and maintenance costs for everyone else. The upstream mechanism is documented in Chroma's Context Rot report26: every frontier model becomes unreliable as input length grows. SWE Context Bench13 adds the corollary — quality of context, not quantity, improves accuracy and cost.

AI amplifies the quality of the engineering system it operates within.

— DORA 2025 report on AI-assisted development8

Organizations with mature systems get leverage. Organizations with fragmented systems get accelerated drift. A dark factory cannot depend on tacit human memory to repair that gap.

The diagnosis has converged across academia and industry inside a five-month window. Kos'myna et al. at MIT Media Lab27 introduce the term cognitive debt with EEG evidence: across four sessions, LLM users showed the weakest brain connectivity and underperformed at neural, linguistic, and behavioral levels. Simon Willison15 operationalizes it from 30 years of practitioner experience: "losing a firm mental model of what the applications can do, which means each additional feature becomes harder to reason about." Storey9 extends to the Triple Debt Model and names intent debt as the load-bearing missing object. Lee et al. at Microsoft Research and Carnegie Mellon28 survey 319 knowledge workers and document the mechanism — by automating routine work and leaving exception-handling to humans, AI atrophies the very judgment exception-handling requires. Anthropic's own sociotechnical study of work inside Anthropic18 names this contradiction the paradox of supervision: effectively using Claude requires supervision, and supervising Claude requires the very coding skills AI overuse erodes. Six different names — cognitive debt, intent debt, comprehension debt, paradox of supervision, scaffolding fragility, slop — for the same gap. The field has converged on the diagnosis. It has not converged on the implementation. codæ is the implementation.

Why local fixes fail

The default response to drift is local steering: better prompts, sharper instructions, more elaborate rules files, stricter reviewer checklists. This works for one run. It dies on the next agent, the next session, the next contributor, the next context window.

Chat history is not memory. A prompt is not authority. The next agent does not reliably inherit what the last one was told; every cycle re-derives the system from partial context, and the durable artifact becomes the codebase itself — too large for any human or agent to re-internalize. Karpathy, in the same talk that named "agentic engineering," concedes the point: "agent workflows need docs, memory, project files, rules, tests, and clear feedback loops."25 That sentence is the requirement spec for a contract. Matt Pocock makes the complementary point at AI Engineer 2026: software fundamentals — explicit interfaces, durable contracts, named invariants — matter more in the agentic era, not less.22

Code review is not the control system either. If humans must repeatedly enter generated implementation to restore coherence, the factory is not dark — and the speedup collapses into manual inspection. The cost is measurable: an Anthropic study cited by O'Reilly5 finds developers using AI assistance score 17% lower on comprehension after equivalent tasks, with the largest decline in debugging.

Making code cheap to generate doesn't make understanding cheap to skip. The comprehension work is the job.

— Addy Osmani, O'Reilly Radar, Apr 20265

The strongest contemporary critique of spec-driven approaches reaches the same conclusion from the opposite direction. Lars Faye's Agentic Coding is a Trap1 — viral in May 2026 (~391 HN points) — argues that current SDD scaffolding fails because "what you say is often not what you mean, and LLMs fill in ambiguity with assumptions (or hallucinations) — more review, more agent revisions, more tokens burned, more disconnection." The diagnosis is right: prose specs leak intent at every ambiguity surface, and probabilistic generators amplify the leakage. Faye's prescription is to retreat — keep humans writing code by hand, treat AI as a delegation utility. codæ shares the diagnosis and rejects the prescription. The right answer to fragile scaffolding is not "no scaffolding"; it is scaffolding that does not fail his test — a multi-tier contract graph with stable IDs, typed obligations, explicit derivation links, and structural checks that close the ambiguity surfaces prose leaves open. The trap is not contract-driven engineering; the trap is contract-driven engineering done with a prose-shaped contract.

Drift is not a vague quality problem. With a contract in place, it becomes a concrete contract violation: detectable, attributable, localizable, and repairable at the contract boundary, before humans are pulled back onto the floor. The fix must be more durable than chat and smaller than code — a maintained contract that agents can consume and humans can repair.

§5 — The mendable surfaceMove human control above implementation.

The dark factory stays dark only while humans stay above the code. The load-bearing question is not how many lines a human can review, but how many meaningful items they can hold in the affected review cut — code-level (files, classes, functions, branches, tests, dependency edges) versus contract-level (capabilities, constraints, requirements, flows, bounded contexts, interfaces, behaviors, decisions, obligations).

Code grows as features × accumulation: every branch, retry path, glue layer, integration adds items. Human comprehension does not scale linearly with it. The working-memory ceiling is hard — humans plateau around 7±2 elements. Brooks's classic distinction between the essential complexity of specifying what a system must do and the accidental complexity of implementing it31 names the partition the contract relies on: the contract holds the essential at human scale; agents handle the accidental.

The contract is a different shape — it captures what the system is, what must remain true, and what generated artifacts must satisfy. A small set of concepts at the right abstraction level governs a much larger set of implementation paths. That is why the contract, not the code, is the human-mendable surface.

Cognitive surface, to scale. A 108K-line system lies far above any human comprehension ceiling. The contract governing it — intent, requirements, structure, behavior, config — is roughly 24% of the code volume and fits below the ceiling. Humans mend the contract. Agents extend the implementation.14

One empirical anchor — using lines as a coarse proxy for items: Vasilopoulos's 2026 field study reports a 108K-line C# distributed system governed by ~660 lines of hot-memory constitution, 19 specialized agents (~9,300 lines), and 34 on-demand spec documents (~16,250 lines), across 283 sessions.14 Even by the cruder line-based proxy, the contract is a fraction of the code and is sufficient to keep agents pattern-adherent at scale.

Cognitive-load-aware refactoring research3 confirms it from another angle. Across 974 MBPP programs, 5,000 APPS programs, and a human study of 20 programmers, structures aligned to working-memory limits reduce failures by 54–71% versus unconstrained prompting and improve comprehension scores by 17–31%. Structure that fits the cognitive surface is not decoration — it is a performance lever.

"Treating project documentation as infrastructure rather than artifact: living specifications that AI agents depend on to produce correct, convention-adherent code."

— Vasilopoulos, Codified Context, Feb 202614

§6 — The durable objectThe contract is memory. The contract is eval.

Once the contract exists, it does more than describe the system — it becomes the durable memory the next agent inherits and the eval surface every generated artifact is checked against. Both are prerequisites for the dark factory.

The contract as long-term memory

When chat is cheap and context is rotting, the only persistent representation of "what this system is supposed to be" is the contract. Anthropic's 2026 Agentic Coding Trends Report12 puts it bluntly: engineers use AI in ~60% of work but can fully delegate only 0–20%. The constraint isn't model capability — it's context.

The gap isn't capability. The gap is that fully delegating a task requires the agent to have the right context to complete it.

— Anthropic, 2026 Agentic Coding Trends Report12

SWE Context Bench13 tests the same mechanism on 1,100 tasks across 51 repositories and 9 languages: correctly selected, summarized context — distilled intent and structure — improves resolution accuracy and reduces runtime/token cost. Unfiltered context provides negative benefit. The contract is curated, high-signal context, durable across agents and sessions.

The contract as eval signal

The same contract checks what agents produce. Specs, code, tests, migrations, infrastructure, traces — every downstream artifact can be verified structurally (does it derive from the right upstream obligations?) and semantically (does it preserve the intended meaning?).

REA-Coder2 tested the shape directly: align requirements before generation, verify after, iterate on misalignments. Across 4 LLMs and 5 benchmarks, the result was 7.93%–30.25% Pass@1 improvement. The binding constraint on code-generation quality is not model capability but requirement understanding. Fix the contract; the code follows.

The contract is the right layer to delegate from

The empirical case against dark-factory coding is usually framed as "humans atrophy when they let AI do the work." Anthropic's coding-skills RCT17 tested the claim — and the finding is sharper than the framing. Across 52 engineers learning the unfamiliar Trio async library, the AI group scored 17% lower on mastery (50% vs 67%), with the largest gap in debugging. The load-bearing sub-finding: those who used AI for conceptual inquiry scored 65%+; those delegating code generation scored below 40%. The data does not say AI assistance causes atrophy — it says the layer at which work is delegated determines whether skill is preserved. Conceptual delegation (asking the agent to explain, compare, clarify intent) leaves cognitive musculature intact; code-generation delegation does not.

The atrophy is not about whether humans delegate to agents. It is about at which layer.

— Reading of Anthropic's coding-skills RCT17

The codæ contract is precisely that layer. Humans stay above it — clarifying intent, refining obligations, mending the graph, judging trade-offs the contract cannot decide on its own. That is conceptual delegation, which the RCT shows preserves skill. Below the contract, agents do the work the same study shows degrades skill when humans do it: generating code, testing, refactoring, repairing failures. The contract is not just memory or eval signal — it is the boundary that makes the human-AI division of labor stable instead of corrosive. The paradox of supervision18 dissolves when humans supervise the contract rather than the code.

This does not prove contract-driven agentic engineering eliminates drift end-to-end. It supports the mechanism: align against a contract before generation, verify after, and keep humans at the layer the data shows preserves judgment. Drift becomes a contract violation — detectable, attributable, localizable, repairable — before humans are forced back into implementation.

§7 — The ladderToward a decidable contract.

codæ is an hommage to Bertrand Meyer's Design by Contract32, not an equivalence. Meyer made obligations explicit between software elements through preconditions, postconditions, and invariants — and made many of those obligations decidable: boolean-checkable at runtime, sound for the property they encoded. codæ inherits the discipline of explicit obligations and the principle that downstream artifacts must satisfy upstream contracts. Full decidability is not inherited yet — the trajectory is to climb toward it.

Rung 1

Semantic eval

Heuristic. Requirement alignment, intent preservation, architectural fit, omitted obligations, hidden conflicts, explanation quality. Agent-judged where machines can't yet decide. This is where most of the contract is checked today.

Rung 2

Mechanical runners

Validation runners — type checks, tests, linters, migrations, policy checks, infrastructure validation, interface conformance, smoke tests, deployment probes. Project-defined; orchestrator-invoked.

Rung 3

Structural checks

Decidable. IDs, schema validity, contract-graph edges, coverage, traceability, artifact provenance, dependency consistency, absence of unresolved contradictions. The engine performs these without an LLM.

The climb goes upward. Each release should promote checks: heuristic dimensions become mechanical runners; mechanical runners become structural rules. The decidable share of the contract grows as the engine matures.

The compiler was software's first dark factory.

Software has done this climb before — one level down. We used to inspect generated machine code; now we inspect source, trust the toolchain, debug through traces. The compiler is the canonical dark factory: humans write source, the toolchain compiles, nobody reads the assembly. We trust it because its contract is decidable.

codæ proposes the same move one level up: humans inspect the contract; agents compile it into implementation. The artifact parser is the frontend, the Contract Graph is the IR, traces are source maps, and generated code targets a platform contract — AWS, GCP, Cloudflare, or a local runtime. The analogy is not a proof (a compiler is deterministic; agentic generation is not) but it clarifies the desired control surface. The long-term ambition is what Meyer's discipline pointed at: formally verifiable software, this time at contract scope. That destination is years away. The ladder is the climb.

§8 — The betGenerated implementation is not the source of truth.

The choice underneath codæ is binary, and worth saying out loud.

One option: keep code human-mendable. The agent drafts; the human reviews, edits, ships. Useful — but not a dark factory. The moment humans must repeatedly enter generated implementation to restore intent or behavior, the speedup collapses into manual inspection.

The other option: code is generated, regenerated, and treated as downstream infrastructure. The contract is what humans maintain, what agents satisfy, what detects drift, what receives repair. This is the codæ bet.

Foundations

  1. Domain-Specific Languages. Fowler, M. & Parsons, R. (Addison-Wesley, 2010). The canonical book-length treatment of DSLs as structured languages purpose-built to capture intent in a form more rigorous than prose and cheaper than full formal specification — the technical lineage the codæ contract belongs to. 2010 · martinfowler.com/books/dsl.html
  2. Domain-Driven Design: Tackling Complexity in the Heart of Software. Evans, E. (Addison-Wesley, 2003). The lineage for bounded contexts, ubiquitous language, aggregates, and the broader vocabulary the contract stack uses to give a system its domain shape. 2003 · domainlanguage.com/ddd
  3. No Silver Bullet — Essence and Accident in Software Engineering. Brooks, F.P. (IEEE Computer, 1987; reprinted in The Mythical Man-Month, 20th Anniversary Edition, 1995). Distinguishes the essential complexity of specifying what a system must do from the accidental complexity of implementing it — the foundational argument behind the cognitive-surface case for contracts. 1986/1995 · No Silver Bullet — overview
  4. Design by Contract. Meyer, B. (Eiffel Software). The foundational discipline of explicit obligations between software elements via preconditions, postconditions, and invariants — the contract pattern codæ generalizes from routine scope to system scope. eiffel.com/values/design-by-contract
