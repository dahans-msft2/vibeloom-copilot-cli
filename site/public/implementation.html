How VibeLoom Is Implemented

Two layers: an agent-side skill that handles semantic judgment and user interaction, and a deterministic Python engine that handles parsing, graph construction, and hash-based drift detection.

Overview

Two Layers

The skill is where agent reasoning lives; the engine is where deterministic computation lives. The two communicate through a small CLI surface and a shared filesystem state.

The engine handles anything that can be decided mechanically — parsing, reference integrity, coverage, hash-based drift detection. The skill handles anything that requires semantic judgment — whether a downstream story faithfully represents its upstream requirement, whether naming aligns with the ubiquitous language, whether a capability is substantively addressed.

Skill

Skill Layer

The skill is a small set of markdown files loaded into Claude Code or Codex. It decides which references and templates to load per operation, routes subagent dispatch, and composes the final response to the user.

SKILL.md maps each operation to the minimal set of references to load. Everything else stays out of context until needed:

Subagent execution contract▶

When work can be decomposed — a component wave, a reconcile fix phase, a parallel import analysis — the orchestrator dispatches subagents. Each subagent runs in one of two modes:

  • read-only analysis — scoped import analysis, eval, advisory review, drift analysis inside reconcile. No write scope.
  • write-capable generation / reconciliation — contract, context, and code generation; bounded-fix phases of review; fix phases of reconcile. Explicit write scope.

Each invocation starts from a fresh prompt built from: the task header (operation, target, scope, objective, write permissions, prerequisites, validation contract, result-shape), the scoped load set, and minimal accepted prior-wave summaries. Same-wave outputs cannot be read as input until the wave is accepted. Late-fetch is capped at one re-invocation per task.

Semantic eval prompts▶

references/eval.md defines the four semantic-eval dimensions and a unified finding schema. Prompts are written declaratively — what to validate, not how — so they remain stable as models improve:

  • Faithful representation — does downstream narrow, widen, or reverse upstream meaning?
  • Naming consistency — does terminology align with the TERM-#### domain model?
  • Implicit dependencies — are there missing derives_from edges the downstream depends on?
  • Capability gaps — are any CAP-#### / CST-#### items unaddressed in the stack?

Findings are returned in a fixed schema: {severity, dimension, upstream_id, downstream_id, message, suggested_fix}. Severity is breaking (escalates delegated auto-advance) or advisory.

Engine

Engine Layer

The vibeloom-engine Python package (version 0.2.0) is the deterministic substrate. It parses artifacts, builds the context graph, and implements structural eval, staleness, and direct-edit detection. It makes no semantic judgments.

CLI surface▶
vibeloom-engine parse --repo <path> Parse all artifacts; print typed JSON inventory
vibeloom-engine graph --repo <path> Build + persist the graph cache (preserves approval snapshots)
vibeloom-engine eval --repo <path> [--target <tier>] Run 9 structural checks; non-zero exit on blocking findings
vibeloom-engine affected --repo <path> --ids <IDs...> Forward DAG walk from changed item IDs
vibeloom-engine staleness --repo <path> Per-item hash diff + forward DAG walk; returns stale artifacts
vibeloom-engine detect-edits --repo <path> Two-tier compare: filesystem mtime fast-filter, per-item hash authoritative
vibeloom-engine status --repo <path> Emit + persist a status snapshot
What the engine does NOT decide▶

The engine is strictly mechanical. It does not decide product meaning, whether a story faithfully represents a requirement, which interpretation of an ambiguous intent to adopt, or whether a drafted artifact is "good enough". All of those belong to the skill and the approval-gated workflow. Template materialization is also skill-invoked subagent work — the engine neither writes nor reads templates.

Data Model

Graph + Approved-State Snapshots

The context graph holds artifacts, items, and derives_from edges. Alongside it, the engine stores a per-artifact approval snapshot — the approval-time mtime and canonical hash of every item inside every approved contract artifact. Both detectors (staleness, direct edits) are grounded in this snapshot.

Cache schema▶
FieldShapePurpose
artifacts{ artifact_id → artifact }Frontmatter, items, current filesystem mtime per artifact
items{ item_id → item }Item type, body, derives_from, owning artifact_id
edges[{ source, target }]Materialized item-level derives_from edges
approved_snapshots{ artifact_id → { mtime, item_hashes } }Per-approved-artifact mtime and canonical item hashes
Canonical item hash▶

An item's canonical hash is a SHA-256 over a normalized JSON representation of its fields:

  • item_id is excluded — it's the lookup key, not content; a rename surfaces as remove + add, not a content match
  • derives_from is sorted lexicographically — derivation is a set, not a sequence
  • Remaining fields (item type, section, description, scope, artifact_id, extra columns) are serialized with JSON sort_keys
  • Volatile frontmatter on the owning artifact (path, mtime, approval timestamp, status) is not part of the item hash — it changes during normal lifecycle transitions and must not cause false drift
Snapshot lifecycle▶

A snapshot for an artifact is:

  • captured the first time the engine sees the artifact with status: approved and no prior snapshot
  • preserved across cache rebuilds for as long as the artifact remains approved — even if its current filesystem state has diverged (this is what makes direct-edit detection work)
  • dropped when the artifact transitions to draft (e.g., after a direct edit is detected and the skill reopens it)

The next approval re-captures a fresh snapshot from the new approved state. No explicit "capture approval" command is needed; the engine infers transitions from status frontmatter on each run.

Drift

Drift Detection — Three Mechanisms

The three drift forms from the methodology (structural, lifecycle, semantic) map to three concrete detectors. The first two run in the engine; the third runs in the skill.

generate or reconcile engine LIFECYCLE approved file edited detect-edits fast filter: mtime equal → skip confirm: per-item hash added / removed / modified auto-reopen to draft → user re-reviews engine SEMANTIC meaning shifted semantic eval 4 dimensions: faithful-repr, naming, implicit deps, cap gaps breaking / advisory findings (blocking or not) → reconcile agent
Why mtime is a short-circuit, not a fallback▶

Detection is authoritatively node-level via content hash. Filesystem mtime is a performance short-circuit: when a file's current mtime equals its approval-time mtime, we know the content is byte-identical and skip the hash comparison. When mtimes differ, we re-hash every item and classify changes as added, removed, or modified. Every reported edit goes through the hash check — nothing is reported from mtime alone.

Cosmetic edits (whitespace, non-semantic frontmatter) pass the mtime filter but match on every hash, so the artifact stays approved and no reopen is triggered.

Eval

How Eval Layers Compose

Each eval invocation runs two passes. The engine's structural pass is blocking: if any of the nine mechanical checks fails, the target cannot advance to approved. The agent's semantic pass is informational and classifies findings as breaking (escalates in pm/dev delegated modes) or advisory.

Pass order and stopping rule▶
  1. Engine structural pass — fast, deterministic. If blocking findings are present, the approval gate is closed and the target must be reviewed and fixed before proceeding.
  2. Agent semantic pass — runs regardless of structural result, but its findings never override structural failures. Breaking semantic findings escalate in delegated modes (pm, dev); in expert they flow into the user review anyway.
  3. Combined report — the skill merges both finding lists into one response with severity-sorted items and specific IDs.

See Methodology → Eval Framework for the full list of structural and semantic checks.

Storage

Storage — Flat JSON, Regenerable

The engine persists derived state to two JSON files in the target repo. Both are regenerable; the markdown artifacts are the ground truth.

PathContentsWhen rebuilt
.vibeloom/state/context-graph.jsonArtifacts, items, edges, approved_snapshotsOn artifact change, context regeneration, or status / derivation-metadata change
.vibeloom/state/status.jsonLifecycle, freshness, coverage, affected scopes, current modeOn every status invocation
Why JSON and not a database▶

The engine is a short-lived CLI, not a service. JSON is human-readable, git-friendly, requires no runtime dependencies, and loads in milliseconds even for large graphs. The state file is a cache — if it's missing, corrupted, or fails validation, the engine regenerates graph structure from the markdown artifacts (the source of truth). Only approved_snapshots represent frozen past state that can't be recovered — losing them means the engine treats the current state of approved artifacts as the new approval baseline.

Cache vs. ground truth▶

The markdown artifacts are always the source of truth. The graph cache is a derived view — rebuildable on demand. This means the engine can be audited, inspected, and version-controlled transparently. It also means the engine stays portable: clone a repo, install vibeloom-engine, run graph, and you have the full state reconstructed.

Install

Install + Verify

  1. Clone the repo 
    git clone https://github.com/ilya-baimetov/vibeloom
cd vibeloom
    No pip install, no dependencies. Python 3.10+ is the only requirement — the engine is pure Python with its own minimal frontmatter parser.
  2. Verify the engine runs 
    PYTHONPATH=v02/engine python3 -m vibeloom_engine --version
# vibeloom-engine 0.2.0
  3. Use the skill Open Claude Code or Codex inside a project. The VibeLoom skill in v02/ is picked up automatically and invokes the engine via python -m. Run /vibeloom init --mode pm to bootstrap a governed project, or /vibeloom import --mode pm to reconstruct a contract from existing code.

Zero install. Zero dependencies. Pure Python.

No API keys. No subscription fees. No runtime service to operate.
