The Problem

AI agents generate local momentum.
They lose long-term coherence.

The first generation pass can look impressive. The twentieth is where the real cost appears: meaning shifts, old decisions disappear, and every new agent has to rediscover what the software is supposed to be. Four named failure modes show up again and again.

01 Semantic drift

Concepts and invariants mutate quietly as prompts pile up. Code still compiles, but it no longer represents the same product.

02 Invisible governance

Intent lives in chat history. There is no durable review surface, no approval trail, no answer to "who decided this and when?"

03 Context fragmentation

The codebase outgrows one agent's window. No agent holds the whole picture; ownership becomes informal, then guesswork.

04 Reconciliation failure

When code and spec diverge, there is no defined procedure for which wins, where to fix it, or how to verify the fix actually closed the gap.

The Bet

Implementation is going
dark factory.
Intent isn't.

Every coding agent gets better every quarter. The implementation gap is closing fast — and any tool whose value depends on directing the model's coding choices ages with the model that supplanted yesterday's. What stays unique to your business isn't how code gets written; it's what you're building, and why.

As agentic codebases scale, managing that contract — intent, requirements, domain, architecture — becomes the load-bearing engineering activity. Other tools double down on directing implementation: per-feature workflows, IDE scaffolds, prompt pipelines. They're betting against the model curve. VibeLoom bets with it.

The shift is already underway. Tessl — which launched as a per-file spec-as-source tool — visibly pivoted in early 2026 to a package manager for agent skills and context. The per-file implementation-control story didn't survive contact with smarter agents. Academia followed: a March 2026 paper names the same problem.

"Semantic intent divergence: a primary yet formally unaddressed root cause of multi-agent failure in enterprise settings."

— arXiv 2604.16339 · March 2026

The contract is the moat. Build it once,
evolve it forever, let the implementation be cheap.

The Model

Contract.
Context.
Code.

Three layers, in that order. The contract is governed truth. Context tells worker agents how to act inside their scope. Code is generated from both — and judged against the contract upstream, never approved on its own.

Layer 1 governed truth

Contract

What you and the agent agree on, gated by approval. The durable source of meaning that survives chat history, contributor turnover, and architectural revisions.

Who owns itYou — through approval gates. The agent generates and validates against approved upstream.
Layer 2 execution truth

Context

Configs, decision records, and behavior specs derived from approved contract. Worker agents read it to know exactly how to act inside their scope — no chat-history archaeology required.

Who owns itGenerated. No approval. If it's wrong, fix it upstream in the contract.
Layer 3 executable

Code

Source, tests, runtime — produced by scoped subagent waves working in parallel. Cross-scope coherence is verified after each wave; failures reopen the affected components.

Who owns itGenerated. Judged against upstream contract — never approved as a separate tier.

Drift Detection

Three forms of drift.
Each one detected.

Other tools generate specs that go stale silently. VibeLoom names three drift forms and detects each one — two deterministically in the engine, one with the agent's semantic eval. False positives are acceptable; false negatives are not.

The same three drift forms — semantic, coordination, behavioral — were independently named in arXiv 2601.04170 (Jan 2026).

01 · Structural

Upstream changed

An approved upstream item was modified or removed since the downstream artifact was last synchronized to it.

How it's detected
Content diff against the approved snapshot, propagated forward through the derivation graph. Caught deterministically on the next pass.
→ Engine · deterministic
02 · Lifecycle

Approved file edited directly

An approved contract artifact was edited outside the normal flow. Auto-reopens to draft so downstream tiers can't derive from unreviewed truth.

How it's detected
The current file is compared against approved state. Whitespace and non-semantic edits don't trigger a reopen.
→ Engine · deterministic
03 · Semantic

Meaning shifted

Downstream content no longer faithfully represents upstream meaning even when the structure passes. The judgment call.

How it's detected
Agent eval across four dimensions — faithful representation, naming consistency, implicit dependencies, capability gaps. Findings are breaking or advisory.
→ Agent · model-reasoned
Four Modes

A compact stack — intent + defaults + flat system. One approval gate at intent. Everything else auto-advances.

How it compares

Beyond spec-driven
development.

Three tools, three bets, one shared assumption: the agent still needs detailed instructions for the next feature. We disagree. As code generation goes dark factory, the only artifact a human still needs to maintain is the blueprint — what the system is, not how the next feature gets built.

Spec Kit and Kiro keep humans in the loop on the factory floor: per-feature specs that drive one generation cycle, then ship and go static. Their durable layers — constitution, steering files — are thin. Tessl pivoted away from per-file spec-as-source because that fight ages with the model; their bet is on per-skill context — the right direction at the wrong scope. VibeLoom is the only one of the four with a whole-system, structured, human-verifiable contract that survives every regeneration and is graph-connected from intent down to component.

Common Questions

The honest answers.

What you'd ask before adopting another AI-coding tool. Including when not to use this one.

When should I not use VibeLoom?

Throwaway scripts, weekend demos, single-file utilities, hackathon work. Prompt-only generation is faster and sufficient. VibeLoom is for projects expected to survive, evolve, or involve more than one agent or contributor.

How is VibeLoom different from spec-driven development tools like GitHub Spec Kit, Kiro, or Tessl?

VibeLoom belongs to the broader spec-driven development family but goes one step further: contract-driven, not just spec-driven. Other spec-driven tools generate specs that decay after one feature. VibeLoom keeps the contract load-bearing across the lifecycle — derivation, eval, drift detection, reconciliation, traceability across components. Tessl wins inside one file; VibeLoom wins across files and tiers. See the full comparison.

What is spec-driven development?

Spec-driven development is a workflow pattern where structured specifications are written before code and used to drive AI-assisted code generation — popularized by tools like GitHub Spec Kit, AWS Kiro, and Tessl. VibeLoom extends this pattern into contract-driven development: the entire spec stack becomes a living contract that governs the codebase across every change, not just the first generation pass.

Won't another prompt cycle just fix the drift?

Better prompts help one run. A contract stack helps future runs inherit approved meaning, scoped context, and known boundaries — without relying on chat memory. Drift is a structural problem; prompts are a tactical fix. Baltes et al. (arXiv 2603.27249, 2026) frame the cumulative cost of AI slop as a tragedy of the commons: individual prompt-level wins externalize onto reviewers, maintainers, and the codebase. Better prompts don't survive the next chat. A graph-connected contract does.

Does it work with Claude Code and Codex?

Yes. VibeLoom ships as a Skill that loads automatically inside both. Zero install. Python 3.10+ is the only requirement for the deterministic engine — no pip install, no runtime dependencies.

Can I adopt it on an existing AI-coded codebase?

Yes. /vibeloom import --mode <mode> reconstructs a candidate contract bottom-up from existing code. You still review and approve top-down. Brownfield is a first-class path, not an afterthought.

Do I need DDD experience to use it?

For vibe mode, no — it skips the domain-model formalism entirely. For pm, dev, and expert modes, vocabulary like bounded contexts and ubiquitous language matters. Start in vibe; upgrade when the project earns the ceremony.
