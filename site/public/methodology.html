Context

Why these terms matter

Spec-driven, contract-first, and contract-driven approaches are gaining attention because teams want AI-assisted development to stay reviewable, traceable, and coherent as systems grow.

What do these terms mean in practice?▶
  • Spec-first means requirements and design artifacts are created before implementation starts.
  • Spec-driven means those specs continue to guide implementation, evaluation, and change management after planning.
  • Contract-first means interfaces, invariants, and acceptance boundaries are defined before code is generated.
  • Contract-driven means those contracts remain active constraints on downstream code, tests, and reconciliation.

Foundation

Core Thesis

The principles that underpin everything VibeLoom does.

1. Prompts are not contracts▶

Prompt-first generation is insufficient for long-lived systems. A natural-language prompt is vague by nature and cannot serve as a verifiable contract. Multiple semantic layers are missing between "build me a scheduling app" and the code that implements it: requirements, user stories, domain model, architecture decisions.

2. AI makes specs economically viable again▶

Historically, teams were lax about maintaining high-quality specifications — the overhead was too high. With AI agents, generating and maintaining structured specs is cheap. This doesn't mean returning to 200-page requirements documents. It means concise, structured specs that humans can scan in minutes, verify, and spot-edit.

3. Upstream specs must be evals▶

Every derived artifact and every implementation unit is checked against its upstream contracts. This is the enforcement mechanism — not aspiration, but concrete evaluations with defined pass/fail criteria and blocking behavior.

4. Modules enable multi-agent development▶

Breaking the application into modules scoped to bounded contexts enables parallel agent work, controls context window usage, and provides clear ownership boundaries. Each module fits in one agent's context window. Interface contracts prevent incompatible APIs between agents working in parallel.

5. Workflow semantics and domain semantics must stay separate▶

The User Story Map (USM) captures workflows, user value, and acceptance criteria. The Domain Model (DM) captures entities, relationships, and invariants. Both are mandatory in every profile. Merging them hides workflow mistakes inside semantic models or buries domain rules inside user stories. Keeping them separate ensures each layer can be reviewed, evaluated, and evolved independently.

Architecture

The Contract Stack

Five tiers from user intent down to running code. Each tier derives from the approved tier above. Upstream items serve as the eval basis for downstream work.

System-specssystem.md, containers.md, per-container + per-componentRuntime actors, trust boundaries, container / component inventory with typed interfacesEXT-, TB-, SNFR-, CONT-, CMP-, IF-, DEP-, BEH-

Why stable, typed IDs matter▶

Every graph entity gets a short, machine-parseable ID of the form PREFIX-#### (e.g., STORY-0003, CMP-0012). Numbers are append-only within each prefix family; deleted IDs are never reused. This lets the engine build a concrete derivation graph where every derives_from reference points at a real, typed upstream item — and every structural eval check (reference integrity, coverage, stack order) becomes fully mechanical rather than "does this look right?".

Why the domain model is the semantic anchor▶

dm.md defines bounded contexts, aggregates, entities, value objects, and invariants as seen by system users — not internal technical details. It captures user value independently of implementation choices. The domain model is the most stable layer: UIs change, APIs change, databases change, but "a Customer has Orders which contain LineItems" rarely does. System-specs derive component boundaries from the bounded contexts declared here.

Workflow

How It All Fits Together

Generation flows top-down. Evals check bottom-up. Human approval gates bracket intent, the product batch, and the spec layer.

Scaling

Four Modes

VibeLoom offers four modes that pick the right level of ceremony for the project. Mode is chosen at init; you can upgrade from vibe to a full mode later.

vibe

Compact, intent-centric
  • ✓ Single user gate: intent-specs
  • ✓ No product-specs tier
  • ✓ Compact system auto-advances internally
  • ✓ Heuristic eval (no explicit graph)
  • ✓ Best for prototypes, solo work

pm

Product-focused, delegated system
  • ✓ User gates: intent + product-specs
  • ✓ system-specs delegated with breaking-change escalation
  • ✓ Full graph-backed eval
  • ✓ Parallel component waves
  • ✓ Best for PM-led feature work

dev

Dev-focused, delegated product
  • ✓ User gates: intent + system-specs
  • ✓ product-specs delegated with breaking-change escalation
  • ✓ Full graph-backed eval
  • ✓ Parallel component waves
  • ✓ Best for devs steering the system

expert

Full gates, nothing delegated
  • ✓ User gates: intent, product, system
  • ✓ Nothing auto-advances
  • ✓ Full graph-backed eval
  • ✓ Maximal human oversight
  • ✓ Best for regulated or critical systems
Delegated auto-advance + breaking-change escalation▶

In pm and dev, whichever tier is delegated auto-advances after structural eval passes and no breaking semantic change is detected against approved truth. A breaking change — item deleted, field changed, interface semantics changed, invariant weakened or strengthened — halts auto-advance and escalates to explicit user review.

In vibe, compact system-specs uses the same safety tests but never becomes its own public approval stop. Structural blockers halt downstream generation; non-blocking findings surface with an upgrade recommendation.

Quality

Eval Framework

Specs aren't documentation — they're verification contracts. Eval runs in two layers: a deterministic engine (structural, blocking) and an agent pass (semantic, breaking or advisory).

LayerWhoWhat it checksOutcome
StructuralEngine9 mechanical checks: reference integrity, coverage, stack order, schema, componentization fit, context sufficiency, etc.Blocking
SemanticAgent4 dimensions: faithful representation, naming consistency, implicit dependencies, capability gapsbreaking or advisory
Engine structural checks (blocking)▶
  1. Lifecycle consistency — draft / approved states align across the approval unit
  2. Reference integrity — every derives_from points at a real item
  3. Required fields — every artifact has the required frontmatter per template
  4. Declared relationships — items owned by correct artifact / scope / tier
  5. Stack integrity — tiers in correct dependency order
  6. Coverage — every non-terminal upstream item has ≥1 downstream derives_from reference
  7. Contradiction (structural) — no downstream item structurally conflicts with its derivation basis
  8. Componentization fit — each component maps to one bounded context; BCs fully contained in a container
  9. Context sufficiency — code-owning components have config; populated containers have container-level config
Agent semantic checks (breaking / advisory)▶
  • Faithful representation — downstream neither narrows, widens, nor reverses upstream meaning. Interface semantics changed, invariant weakened or strengthened → breaking
  • Naming consistency — terminology aligns with the TERM-#### items in the domain model
  • Implicit dependencies — missing derives_from edges where the downstream clearly depends on an upstream item
  • Capability gaps — CAP-#### / CST-#### items entirely unaddressed in the downstream stack

Breaking findings block delegated auto-advance in pm and dev and escalate to explicit user review. Advisory findings surface in the report but do not block approval.

Behavioral scenarios (generated from contract)▶

bdd artifacts capture behavioral scenarios in the context tier, derived from approved STORY- / ACC- / INV- / CMP- items. They are regenerable from approved contract state and are not themselves an approval stop.

Drift

Three Forms of Drift

Drift is any divergence between the current state of the stack and its approved-upstream basis. Three forms are recognized, each with its own detection mechanism.

FormTriggerDetectionRemediation
StructuralApproved upstream item modified or removed since downstream was synchronized to itPer-item canonical hash diff + forward DAG walk from changed upstream itemsgenerate (forward-only) or reconcile (preserves manual edits)
LifecycleApproved contract artifact edited outside the skill's flowFilesystem mtime fast-filter + per-item canonical hash confirmationAuto-reopen to draft (lifecycle bookkeeping); semantic resolution follows
SemanticDownstream content no longer faithfully represents upstream meaning, even when structure matchesAgent-side semantic eval (4 dimensions above)Surfaced as findings; reconcile for user-directed fixes

reconcile is the user-initiated remediation loop for all three forms. generate handles structural drift on the forward-only path. Lifecycle drift is handled automatically by reopening the edited artifact to draft.

Staleness is computed, not stored▶

Staleness is never written into artifact frontmatter. It is a view over current state, derived by comparing current content against the last-approved state of each upstream entity. If a user edits and then reverts, nothing persists incorrectly — the next staleness pass sees the reverted content and reports no drift.

Invariant: false positives are acceptable; false negatives are not. An over-marked stale set causes unnecessary review; an under-marked set lets drift leak silently past approval gates. When in doubt, the system marks stale.

Multi-Agent

Component Interface Contracts

Components aren't just code organization — they are subagent boundaries. Each component fits in one context window with typed, stable interfaces.

Component spec example▶ 
## Component: CMP-0007 (orders)

### Owned interfaces
- IF-0012: createOrder(items: CartItem[], customer: CustomerId) → OrderId
- IF-0013: OrderPlaced { orderId, customerId, total, timestamp }

### Dependencies
- DEP-0021 → CMP-0009 / IF-0034: checkAvailability(sku) → AvailabilityResult
- DEP-0022 → CMP-0012 / IF-0041: chargePayment(customerId, amount) → PaymentResult

### Owned behaviors
- BEH-0009: retries once on transient inventory failure, surfaces error otherwise
Dependency rules & interface ownership▶
  • The cross-component dependency graph must be a DAG (no cycles)
  • An interface is owned by exactly one component; only the owner can change its definition
  • Changing an interface's semantics is a breaking change — caught by both engine (structural diff) and agent (semantic diff against approved version)
  • New cross-component dependencies require a component spec amendment (approval-gated)

When an interface changes: engine marks all downstream components structurally stale → agent evaluates semantic impact → specs regenerate → affected code is re-generated per component wave.

Subagent dispatch contract▶

Each subagent runs in one of two modes with a fresh prompt built from a scoped load set:

  • read-only analysis — used for scoped import analysis, eval, advisory review, and drift analysis inside reconcile. No write scope.
  • write-capable generation / reconciliation — used for contract, context, and code generation, bounded-fix phases of review, and fix phases of reconcile. Explicit write scope.

Subagents may not treat same-wave outputs as input. Same-wave outputs become eligible inputs only after the wave is accepted and the dispatch plan is recomputed. Late-fetch is capped at one re-invocation per task.

Interface

Command Reference

$vibeloom is the state-aware entrypoint. Use explicit /vibeloom commands that follow the abstract model <action> <target> <context> when you want direct control.

/vibeloom init --mode <mode> [seed] Bootstrap an ungoverned repo (vibe | pm | dev | expert)
/vibeloom import --mode <mode> [repo] Reconstruct a candidate contract bottom-up from existing code
/vibeloom generate [target] Forward-back pass generation of the next affected tier from approved upstream
/vibeloom eval [target] Structural + semantic validation against approved upstream basis
/vibeloom review [target] Interactive eval loop with bounded fixes within the target
/vibeloom reconcile [target] User-initiated remediation loop for all three forms of drift
/vibeloom approve [target] Advance a reviewed contract tier from draft to approved
/vibeloom status [scope] Lifecycle, freshness, coverage, affected scope, current mode
Primitive vs interactive operations▶

generate and eval are the two primitives. review is an interactive shell on top of eval; reconcile is an interactive shell on top of generate. Each interactive cycle loops through detect → propose → fix → validate with explicit user exit choices (Loop, Eval only, Proceed to approve / Accept).

Reconciliation is asymmetric▶

Approved upstream contract defines intended meaning. Downstream drift produces proposals, not silent rewrites. For each conflict, the agent offers direction options — amend upstream truth, preserve upstream and correct downstream, or a user-specified alternative — and the user chooses. In practice generate code is the 90% path; reconcile is the surgical review path for when you want to detect, inspect, and preserve manual edits.
