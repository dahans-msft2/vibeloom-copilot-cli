Methodology · v0.2

The contract-driven methodology for AI-coded projects.

VibeLoom turns intent into a tiered, version-controlled contract — durable, derivation-aware, and treated as both source of truth and eval system. This page explains the principles, the artifacts, the operations, and the invariants that hold the stack together.

Core thesis AI-generated systems need a governed contract stack, not a longer prompt. The stack doubles as the eval surface that keeps downstream artifacts coherent across every generation, contributor, and revision.

Principles

VibeLoom rests on four load-bearing ideas. Everything else — the artifacts, the modes, the operations, the engine — is mechanism in service of these.

  1. The system is defined as a contract stack, not a set of stale one-off specs. Specs are a graph of derived items, not a folder of documents.
  2. The contract stack doubles as the eval stack. Upstream items are the basis for downstream work and the criterion against which it's checked.
  3. Agents are responsible for generation and validation, gated by the user. Mode picks where the gates sit; everything between gates is the agent's job.
  4. Scoped context enables agent scaling. Subagents receive bounded load sets, not whole-repo dumps. The context graph makes this safe at scale.

The problem VibeLoom is designed for

AI coding agents create local momentum but struggle to preserve consistency over time. The first generation pass can look impressive; the twentieth is where the cost shows up — meaning shifts, decisions disappear, and every new agent has to rediscover what the software is supposed to be. Four named failure modes show up in any sufficiently large AI-coded project:

  • Semantic drift — concepts and invariants shift subtly with every prompt.
  • Invisible governance — intent lives only in chat history with no durable review surface.
  • Context fragmentation — large codebases exceed one agent's context, making ownership guesswork.
  • Reconciliation failure — manual edits and drift have no principled path back to specifications.

These four failure modes are the entire reason the methodology exists. Every artifact, mode, operation, and engine command in VibeLoom maps to mitigating one or more of them.

The bet: implementation goes commodity, intent doesn't

The history of AI coding tools is a history of compensating for what the model couldn't yet do. Plan-first tools exist because the model wouldn't hold a plan. Per-feature spec workflows exist because the model would skip steps. Steering files exist because the model would forget conventions. IDE scaffolding exists because the model would lose context. Every one of these mechanisms is a workaround for a current limitation — and every one of them becomes overhead the moment the model improves past it.

Look at the ground that's already shifted. Tessl, which launched as a per-file spec-as-source tool — the spec is the only editable artifact, code is regenerated, marked DO NOT EDIT — visibly pivoted in early 2026 to a "package manager for agent skills and context." The per-file implementation-control story didn't survive contact with smarter agents. Their bet now is on context: better instructions, better library knowledge, better evaluation. That's a real bet, and a strong one — but it stops at the skill boundary. There's no artifact in Tessl that says what your system is.

GitHub Spec Kit invests its complexity budget in workflow ceremony — seven phases, slash commands, branch-scoped specs that go stale post-merge. Its constitution is genuinely durable; the rest is scaffolding the model is rapidly outgrowing. Kiro packages the spec/design/tasks pipeline into an IDE with credit billing; its steering files and hooks are useful, but the per-feature artifacts go static the moment they're approved.

The pattern is clear. Tools that double down on directing the model's implementation are betting against the model curve. The model curve is steeper than the tooling curve.

The bet, in one sentence. Implementation is becoming a commodity; intent isn't. The dark factory needs a blueprint, and the blueprint has to outlive the machinery.

VibeLoom bets the other direction. We treat the contract — intent, product requirements, domain model, system architecture, component invariants — as the load-bearing artifact, governed by a context graph that detects when changes upstream make downstream specs stale. The model writes the code; the contract governs whether the code is what you meant. As models get better at code, the contract doesn't become less valuable — it becomes the only thing that's still uniquely yours.

Every section that follows — the contract stack, the context graph, the modes, the operations, the eval and drift mechanisms — exists to make this bet operational. If the bet is wrong, VibeLoom is a more disciplined version of what other tools already do. If the bet is right, contract-driven tools compound while implementation-direction tools age. The downside is bounded; the upside scales with model improvement.

Three-layer architecture: contract → context → code

VibeLoom partitions a governed application into three layers.

contract — governed semantic truth. The user seeds the intent and retains approval-policy authority. Depending on mode, some tiers are explicit user stops while others may auto-advance under delegated rules. The agent generates, validates, and refines the tiered intent-specs → product-specs → system-specs stack. Each tier derives from and is checked against approved upstream truth.

context — definitive execution config for agents, plus read-only change records. These artifacts do not require approval. They are generated only from approved contract truth. Users may inspect, eval, review, and edit them when needed, but if context is wrong, the normal fix path is upstream in the contract.

code — the executable result. Users are not expected to edit code directly. The orchestrator agent reads contract and context, identifies affected scopes, and dispatches scoped worker agents. Each worker receives only the slice of context and contract pertinent to its scope.

Important note on terminology: the context tier in VibeLoom means generated execution truth (configs, decision records, BDD scenarios) — not the LLM's context window. The two are easy to confuse.

The contract stack, in detail

Three contract tiers, plus context and code. Each derives from the approved tier above. Every artifact is parsed into items — capabilities, requirements, stories, components, interfaces, behaviors. Each item carries a stable, prefixed ID, and each derivation between items is declared explicitly in artifact frontmatter as derives_from.

Tier 1 · intent-specs

SpecPurposeGenerated from
intentProse-first description: capabilities and hard constraintsUser request
defaultsRepo-wide constitution: binding global rules, tech baseline, quality guardrailsintent

In vibe mode, intent also carries a product-summary section that seeds future product-specs if the project later upgrades.

Tier 2 · product-specs (absent in vibe mode)

prdObjectives, key results, metrics, functional/non-functional requirementsintent
usmEpics, flows, stories, acceptance criteria, milestonesintent + prd
dmDomain model: bounded contexts, aggregates, entities, value objects, invariants, ubiquitous languageintent + prd + usm

The domain model is the semantic anchor for the whole stack: components are derived from bounded contexts, not from folder shape.

Tier 3 · system-specs

SpecPurposeGenerated from
systemExternal actors, trust boundaries, system-wide non-functional requirementsApproved product-specs
containersRuntime topology: how the system is deployedsystem
container.mdPer-container detail: components inside, internal dependenciescontainers
component.mdPer-component spec: typed interfaces (IF-####), dependencies (DEP-####), behaviors (BEH-####), owned filesystem pathscontainer

Tier 4 · context (derived, no approval)

Generated execution truth: config (CLAUDE.md / AGENTS.md at root, container, and component scope), pdr (product decision records), adr (architecture decision records), bdd (Gherkin scenarios per component).

Tier 5 · code

Source organized by <container>/<component>, tests (unit, integration, BDD), and runtime (packaging, deployment, migrations). Code is judged against upstream — never approved as a separate tier.

The context graph

The contract stack is what you author. The context graph is what the engine builds from it — a single, queryable model of the system, assembled by parsing every artifact's items and following every derives_from edge. Almost every load-bearing operation in VibeLoom — derivation, affected-set computation, drift detection, scoped subagent dispatch — runs on this graph.

Anatomy

Items are the nodes; derives_from declarations are the edges. Together they form a directed acyclic graph: cycles are forbidden, and only capabilities and constraints are valid roots. Every other item, transitively, derives from one or more capabilities or constraints.

Why it's load-bearing

  • Derivation order. The graph determines what to generate next: never a downstream item before its upstream is approved.
  • Affected-set computation. When an item changes, walking forward through derives_from yields every item that may need to follow.
  • Drift detection. The graph is what makes drift locatable — a stale item maps back to its owning artifact, and forward to every artifact that depends on it.
  • Scoped subagent dispatch. The graph makes it safe to run parallel subagents: each agent's load set is a precise slice of the graph; write scopes are disjoint by construction.
  • Traceability. Any code, test, or context file can be traced back to the capabilities and constraints it implements.

How it relates to authoring

You don't author the graph — you author artifacts. The graph is computed: parsed from frontmatter, validated for integrity, persisted as cache. If two artifacts disagree on a derivation edge, that's a structural finding the engine surfaces immediately. If you delete an upstream item, every downstream item that referenced it shows up as broken on the next pass.

This is what makes the methodology enforceable rather than aspirational. Without the graph, contract-driven would be a discipline. With it, it's a substrate.

Four modes

A mode controls three things: which tiers the user explicitly co-authors and approves, which are delegated to the agent, and whether the contract stack is full or compact.

ModeStackUser ownsAuto-advances
vibeCompact (intent + defaults + flat system)intent-specssystem, code
pmFullintent-specs, product-specssystem-specs
devFullintent-specs, system-specsproduct-specs
expertFullall three contract tiersnothing

Vibe → full upgrade is one-way. Run /vibeloom init --upgrade --mode pm|dev|expert to promote a vibe repo to a full mode. Compact intent seeds full prd/usm/dm; flat system expands into the full system + containers + per-component layout. There is no downgrade.

Delegated auto-advance is bounded. Even in vibe, pm, and dev, the agent only auto-advances when the structural eval passes and no breaking semantic change is detected. Breaking change means any mutation to an existing approved item; only adding new items consistent with approved truth is non-breaking.

Eight operations

The CLI surface is intentionally small. generate and eval are the two primitives; the others are interactive shells, lifecycle transitions, or read-only reports.

CommandWhat it does
/vibeloom initBootstrap an ungoverned repo. Picks a mode and an initial intent. A separate upgrade flow promotes a vibe repo to a full mode (one-way).
/vibeloom importReconstruct a candidate contract bottom-up from existing code.
/vibeloom generateForward-back-pass produce the next affected tier from approved upstream truth. Idempotent.
/vibeloom evalStructural plus semantic validation; reports findings, modifies nothing.
/vibeloom reviewInteractive shell on eval — surface findings, propose bounded fixes, loop until you proceed.
/vibeloom reconcileUser-initiated remediation loop for any of the three drift forms. Always user-initiated.
/vibeloom approveAdvance a reviewed contract approval unit from draft to approved.
/vibeloom statusRead-only report of lifecycle, freshness, coverage, affected scope, and current mode.

Plus a $vibeloom shorthand that triages by current state and suggests the next operation. Full CLI syntax — flags, targets, scopes — lives in Implementation · Engine CLI.

Why this works at scale. Because the context graph maps each item to its owning artifact and each component to a disjoint slice of the filesystem, generate can dispatch parallel subagents safely — each with a precise, bounded load set, no cross-talk between writes. The orchestration mechanics live in Implementation · Subagent dispatch.

Generation, approval, lifecycle

Every generation is forward-back within a tier. The forward pass produces artifacts in dependency order. The back pass checks whether later artifacts constrain earlier ones — if a story implies a requirement that wasn't in the PRD, the back pass reopens the PRD as draft and amends it. The loop terminates when nothing more reopens. Generation is idempotent: same approved upstream, same output.

The lifecycle itself is intentionally two states: draft and approved. No in-progress, no review-pending, no published. draft means "not yet trusted as upstream truth"; approved means "downstream tiers may derive from this."

An approval unit is one contract tier — the affected artifact set within it advances together. approve intent-specs moves both intent.md and defaults.md if they're coherent. Tier-level approval keeps related artifacts in sync.

On approval, the engine captures an approved-state snapshot: a per-item content fingerprint of every approved artifact. It's the basis for staleness and direct-edit detection, preserved across rebuilds and discarded only when an artifact returns to draft. (Algorithm and on-disk format: see Implementation · Approved-state snapshot.)

Eval, two layers

VibeLoom has two stacked eval layers. The structural layer is deterministic (engine-side); the semantic layer is judgment-based (agent-side). Both run in eval and review.

Structural — 9 checks (blocking on approval)

  1. Lifecycle consistency — every artifact's frontmatter status matches its tier rules.
  2. Reference integrity — every derives_from resolves to an existing item.
  3. Required fields — frontmatter completeness per artifact type.
  4. Declared relationships — items live in correct artifacts, scopes, and tiers.
  5. Stack integrity — tier order respected; no upward derivation.
  6. Coverage — every non-terminal upstream item has at least one downstream item.
  7. Contradiction — no downstream item directly conflicts with upstream meaning.
  8. Componentization fit (full modes only) — every component maps to exactly one bounded context; every BC sits in exactly one container.
  9. Context sufficiency (full modes only) — every code-owning component has the execution config it needs.

Semantic — 4 dimensions (breaking or advisory)

  1. Faithful representation — downstream content does not narrow, widen, or reverse upstream meaning.
  2. Naming consistency — terms align with the ubiquitous language (TERM-#### in the domain model).
  3. Implicit dependencies — load-bearing references are explicit in derives_from, not hidden in prose.
  4. Capability gaps — every CAP-#### capability and CST-#### constraint is substantively addressed downstream.

The principle behind both layers: false positives are acceptable; false negatives are not. An over-marked stale set causes unnecessary review. An under-marked set lets drift leak silently past approval gates.

Drift, three named forms

Drift is the central concern of v0.2. It comes in three forms, and each has its own detection mechanism.

FormWhat it isDetection
Structural Approved upstream item modified or removed since downstream was last synchronized. Engine: content diff against the approved snapshot, propagated forward through the derivation graph.
Lifecycle Approved contract artifact edited outside the flow. Engine: detects approved-file edits and auto-reopens them to draft.
Semantic Downstream content no longer represents upstream meaning even when structure matches. Agent: 4-dimension semantic eval. Findings are breaking or advisory.

reconcile handles all three. It is the user-initiated loop where conflicts are surfaced with item IDs, the user picks fix direction (amend upstream, preserve upstream and correct downstream, or alternative), and generate is invoked on the affected artifacts. The agent never auto-invokes reconcile.

When to use VibeLoom

VibeLoom is strongest where prompt-only generation stops being reliable. Use it when:

  • The codebase must survive more than one generation step, more than one contributor, or more than one architectural revision
  • Multiple bounded contexts, non-trivial workflows, or meaningful technical boundaries are present
  • Multiple agents or users may work in parallel and need consistent context
  • Semantic coherence matters more than raw generation speed

VibeLoom adds ceremony. For a weekend prototype, single-file utility, or throwaway script, prompt-only generation is likely faster and sufficient. For anything that will be maintained, extended, or shared, VibeLoom pays for itself through reduced drift and explicit traceability.

How VibeLoom compares to spec-driven development tools

VibeLoom belongs to the broader spec-driven development family — alongside GitHub Spec Kit, AWS Kiro, and Tessl — but takes a stronger position: contract-driven, not just spec-driven. Where every spec-driven tool treats specifications as artifacts that drive the next code generation, VibeLoom treats the contract as the load-bearing artifact across the lifecycle.

The right way to compare these tools is to ask where each one invests its complexity budget — because that's where the value lives, and that's what determines whether the value compounds or ages as models improve. Five dimensions, four tools, honest comparison.

Dimension VibeLoom GitHub Spec Kit Kiro Tessl
Where the complexity budget goes Contract graph + reconciliation Per-feature workflow ceremony + constitution IDE + per-feature spec pipeline Reusable context packaging + registry
Scope of governance Whole-system (context graph) Per-feature + global constitution Per-feature + global steering files Per-skill (reusable, cross-project)
What persists across generations Specs evolve, graph-tracked Specs decay, branch-scoped Specs go static post-creation Skills evolve (semver-versioned)
Coupling to current model capability Low — value grows with model quality Medium-high — ceremony scaffolds the model High — workflow keeps the model on rails Low — better models use better context better
Cross-cutting coherence Native (graph + DDD invariants) Constitution only — features don't talk Steering files only — specs are siloed None at system level — skills are independent

Where each tool lands relative to the bet. Spec Kit and Kiro double down on directing implementation per feature, with light global rules layered on top. As models improve, that ceremony becomes overhead. Tessl already pivoted in early 2026 — they walked away from per-file DO NOT EDIT spec-as-source and reorganized around versioned context skills. That move validates the bet from a different angle: managing what the agent knows beats managing what it writes. VibeLoom takes the next step up the same staircase: managing what the system is supposed to be beats managing what each agent invocation knows.

Where each tool wins. Spec Kit is the strongest open-source starting point with the largest community and a genuinely durable constitution mechanism. Kiro is the cleanest auditable per-feature trail for regulated environments inside an integrated IDE. Tessl is the strongest per-skill knowledge distribution layer; if you want to make a single agent invocation 3× more accurate at using a specific library, Tessl is what you reach for. None of these are bad tools — they're betting on different ground.

Where the bet is weakest. Contracts decay too if nobody maintains them; the context graph detects drift but doesn't prevent cultural neglect. The DDD vocabulary in full modes narrows the addressable market. And if Tessl extends upward into system-scope skills, they could occupy adjacent ground. The bet is asymmetric — bounded downside, scales with model improvement. That's a position worth taking.
