codæ

Contract-driven agentic engineering.

Agentic AI coding has dramatically lowered the cost of producing code. It hasn't lowered the cost of holding a system together. As autonomous agents extend codebases beyond what any single human can comprehend, semantic drift accumulates and "AI slop" compounds — measurable, in 2026, in real codebases. This whitepaper makes the case for governing it through a stack of human-mendable contracts: smaller than the code, persistent across agents, and verifiable against what gets built.

§1 — The slop problemGeneration got cheap. Coherence didn't.

Before LLM agents, drift in a codebase was slow and human-paced. A team accumulated technical debt over months and quarters; the rate of change was bounded by how fast humans could type, review, and merge. Coherence was preserved or lost in the open: the people writing the code were also the people holding the mental model, and divergence from intent showed up where they could see it.

Agentic coding broke that bound. A multi-turn agent now extends its own prior code, summarizes its own context, and re-derives its understanding of the system on every turn — at machine speed, without any single human holding the mental model. Every cycle is a chance for meaning to slip. And the slips compound.

The same failure shows up under three names in the 2026 literature:

  • Semantic drift — outputs progressively diverge from original task intent while remaining syntactically valid. Now widely named in 2026 reporting on long-running AI coding.
  • AI slop — code that looks reasonable, passes review-by-glance, and accumulates faster than reviewers can absorb. A 1,154-post analysis of developer-forum discussions coded fifteen recurring themes, all converging on one pattern: cheap to generate, expensive to review.1
  • Comprehension debt — the codebase looks clean, but no human (and no incoming agent) on the team understands what it's doing or why. Coined formally this year in a study of 207 students across 8 weeks of agentic-Scrum projects.2

Three names, one structural problem: the rate at which agentic systems can produce code now exceeds the rate at which humans can integrate it into a coherent whole. Drift is no longer an aberration. It's the equilibrium.

The most precise empirical study published this year is SlopCodeBench3: 20 problems × 93 checkpoints × 11 models, instrumented to measure how agent-written code degrades when agents iteratively extend their own prior code under evolving specs. The finding that deserves to be famous: no agent solves a whole problem end-to-end. Erosion — complexity concentrating in already-bloated functions — rises in 80% of trajectories. Verbosity rises in 89.8%. Agent code is 2.2× more verbose than comparable open-source Python repositories.

The slop pattern is also visible in the wild. Liu et al.13 tracked 302.6k verified AI-authored commits across 6,299 GitHub repositories and identified 484,366 issues introduced; 22.7% of those tracked AI-introduced issues survive at latest revision. The social side has been characterized too: Baltes, Cheong, and Treude1 coded 1,154 developer-forum posts and frame the result as a software-commons problem — generation gains for one developer become review and maintenance costs for everyone else.

The mechanism behind the deterioration is well documented. Chroma's "Context Rot" report4 (a July 2025 technical report, included here because nothing comparable has been published in 2026) tested 18 frontier models including GPT-4.1, Claude 4, Gemini 2.5, and Qwen3: every single one becomes unreliable as input length grows, even on controlled tasks. SWE Context Bench11 adds the corollary — context quality, not quantity, is what improves agent accuracy and cost.

"AI amplifies the quality of the engineering system it operates within."

— DORA 2025 report on AI-assisted development6

Organizations with mature processes get the upside. Organizations with fragmented systems get accelerated drift. The data does not support a neutral case.

Across all of the above, the same shape appears: agentic generation works as a bounded operation but degrades when bound to long-running, multi-component, multi-agent systems where coherence has to be preserved. The bottleneck is not model capability. The bottleneck is the absence of a durable, inspectable, traceable control surface above the code.

§3 — Why prompts don't scaleMore prompts won't save you.

The default response to drift is to fight it locally: better prompts, sharper instructions, more elaborate steering files, stricter rules. This works for one run. It doesn't survive the next agent, the next session, the next contributor.

Chat history is not memory. The next agent doesn't read what you told the last one. Every cycle starts cold, with the codebase as the only durable artifact — and the codebase, by this point, has become too large for any agent or human to internalize from scratch.

The cumulative cost is now measurable. An Anthropic study cited in O'Reilly's reporting7 found that developers using AI assistance scored 17% lower on comprehension quizzes after completing equivalent tasks, with the largest decline in debugging. The codebase looks clean. The reckoning arrives quietly.

"Making code cheap to generate doesn't make understanding cheap to skip. The comprehension work is the job."

— Addy Osmani, O'Reilly Radar, Apr 20267

Prompts are a tactical fix for a structural problem. The structural fix has to live somewhere more durable than the chat window.

§4 — The cognitive surfaceCount items, not lines.

The right way to compare what a human can hold in their head is not lines or tokens — it is the number of meaningful items in the affected review cut. At the contract level, those are IDed semantic items: capabilities, constraints, requirements, flows, stories, acceptance criteria, bounded contexts, views, interactions, components, interfaces, behaviors, decisions. At the code level, the surface is files, classes/types, methods/functions, endpoints/handlers, branches, tests, integrations, runtime resources, and dependency edges.

A codebase grows roughly with features × accumulation: every new branch, edge case, retry path, glue, and integration adds items. Comprehension does not scale linearly with that growth. There's a working-memory ceiling — humans plateau around 7±2 elements, and cognitive-load research formalizes the rest. Above that ceiling, code becomes a foreign object: readable line by line, opaque as a system.

A specification is a different shape. It captures what the system is, not how every line implements it. A small set of concepts at the right level of abstraction can cover a large set of code paths. The spec stack is, by construction, a smaller item surface than the code it governs.

codæ should measure and report the actual ratio:

  • contract_items — IDed contract items
  • affected_contract_items — the affected graph cut for a change
  • affected_code_items — code entities touched or implied by the change
  • review_compression_ratio = affected_code_items / affected_contract_items

Until dogfood data exists, the modest claim is: humans review tens of contract items rather than hundreds or thousands of code items. The ratio should be a reported metric, not a rhetorical flourish.

Cognitive surface, to scale. A 108K-line system (left) lies far above any human comprehension ceiling. The spec stack governing it (right) — intent, requirements, structure, behavior, config — is roughly 24% of the code volume and fits below the ceiling. Humans hold the right side. Agents extend the left. The contract is the bridge.8

One empirical anchor (using lines as a coarse proxy for items): Vasilopoulos's 2026 field study8 reports a 108,000-line C# distributed system governed by ~660 lines of hot-memory constitution, 19 specialized agents (~9,300 lines), and 34 on-demand specification documents (~16,250 lines), across 283 development sessions. Even by the cruder line-based proxy, the spec stack is a fraction of the code and is sufficient to keep agents pattern-adherent at scale. The illustration above shows the rough proportion. Item-count ratios will be reported once vibeloom dogfood data exists.

Cognitive-load-aware refactoring research9 confirms the principle from a different angle. Across 974 MBPP programs, 5,000 APPS programs, and a human study of 20 programmers: structures aligned to working-memory limits reduce failures by 54–71% versus unconstrained prompting and improve comprehension scores by 17–31% across multiple measures. Structure that fits the cognitive surface is not a stylistic preference. It's an empirical performance lever.

"Treating project documentation as infrastructure rather than artifact: living specifications that AI agents depend on to produce correct, convention-adherent code."

— Vasilopoulos, Codified Context, Feb 20268

§5 — Memory and evalSpecs are what survives the next agent.

A spec stack at the right cognitive surface is necessary but not sufficient. The deeper claim is that the same stack, once it exists, does two more things at once: it gives the next agent long-term memory of what the system is, and it gives the generation step an eval signal that what it just produced can be checked against.

Specs as long-term memory

When chat is cheap and context is rotting, the only persistent representation of "what this system is supposed to be" is the spec stack. Anthropic's 2026 Agentic Coding Trends Report10 puts it bluntly: engineers use AI in roughly 60% of work but can fully delegate only 0–20%. The constraint isn't model capability. It's context.

"The gap isn't capability. The gap is that fully delegating a task requires the agent to have the right context to complete it."

— Anthropic, 2026 Agentic Coding Trends Report10

The empirical receipt comes from SWE Context Bench11: 1,100 base tasks across 51 repos and 9 languages. Correctly selected, summarized context — i.e., distilled intent and structure — improves resolution accuracy and reduces runtime/token cost. Unfiltered or wrongly selected context provides negative benefit. Quality of context, not quantity. A spec stack is the curated, summarized, high-signal context the next agent needs.

Specs as eval signal

The same artifacts work as the eval surface. When the agent generates downstream content — more specs, code, tests — everything it produces can be checked against the approved upstream, both structurally (does the new artifact derive from the right inputs?) and semantically (does it faithfully represent the upstream meaning?).

REA-Coder12 tested this directly: align requirements before generation, verify after, iterate on misalignments. Across 4 LLMs and 5 benchmarks, the result was 7.93% to 30.25% Pass@1 improvement. The binding constraint on code-generation quality isn't model capability — it's requirement understanding. Fix the spec; the code follows.

That is not a proof that contract-driven agentic engineering eliminates drift. It is supporting evidence that requirement-alignment-before-generation scales as a real mechanism — not an aspiration — when paired with verification. The pattern is the right shape to lean on.

§6 — The BetCode goes dark factory. Intent stays mendable.

"The 10–100× speedup is real only when the human stays out of the code. The contract is what keeps them out."

Dark factory is a two-to-three-year bet, not a v0.3 promise. Today's agents are not yet trustworthy enough to be left entirely alone with the code. What follows is the trajectory codæ commits to, not the level of guarantee any single tool — including VibeLoom — can deliver right now.

The choice underneath the manifesto is binary, and worth saying out loud.

One option is to keep code human-mendable. The agent generates a draft; the human reviews, edits, and ships. This is the world we lived in for two years, and it is the world the entire industry-promised 10× to 100× productivity lives in. It also has an ugly back-of-the-envelope: if the human ever has to drop into the code to fix what the agent built — even for a small fraction of changes — the speedup collapses. Code's cognitive surface (§4) is what it is. Reading 100,000 lines to safely change 100 of them is not a 100× operation. It is barely a 1× operation. The promise stops working the moment the human is required.

The other option is the bet codæ makes: code becomes the dark factory. It is generated and re-generated. It is not maintained by hand. The human's mendable surface moves up the stack — from the code to the contract above it. The contract is the artifact the human can comprehend, govern, and edit. The code is the artifact the agent compiles down to.

For this bet to work, the contract has to do these jobs at once:

  • Edited by humans — so it must be smaller than the code.
  • Kept consistent and coherent with AI's help — so it must be machine-checkable.
  • The long-term memory the next agent inherits — durable across sessions, independent of chat.
  • The eval signal every generated artifact is verified against — drift becomes detectable, not hopeful.

A stack of mutually-derived complementary specs satisfies all four. That is the codæ proposition. The 10–100× speedup survives only if the human never has to touch the factory floor. Keep them upstairs. Give them a contract.

§7 — The codæ thesisContract-driven agentic engineering.

The threads pull together cleanly:

  • The problem is structural — drift compounds at machine speed under agentic generation.
  • The mechanism is mechanical — chat is not memory, context rots, agents re-derive their understanding every turn.
  • The surface humans can hold is the spec stack — measured by the number of IDed semantic items in the affected review cut, not by lines of code.
  • Contract-style enforcement on agents is now empirically supported (§5) — not yet proven to bound drift universally, but real enough to lean on.

From these, the codæ thesis follows directly: govern agentic code generation by a stack of complementary, human-mendable contracts. The stack is smaller than the code, persists across agents, is verifiable against the code, and is approved by humans. (The methodology spells out how each property is implemented at the artifact level — see VibeLoom methodology. This whitepaper stops at the paradigm.)

From spec-driven to contract-driven

There is a name for the immediate predecessor: spec-driven development, the movement now naming itself across tools like AWS Kiro, GitHub Spec Kit, and BMAD. The 2026 SDD taxonomy15 places existing approaches across three rigor levels — spec-first (specs guide, then drift), spec-anchored (specs and code co-evolve with enforcement), spec-as-source (specs alone are edited; code is regenerated). All three are real progress over prompt-only generation. codæ is the next level: contract-driven — the spec stack is not one source for one file or one feature, but the multi-tier, mutually-derived, drift-detecting contract that governs the lifecycle. Same impulse, larger surface.

The compiler was software's first dark factory

We used to inspect generated machine code. Now we inspect source, trust the toolchain, test the result, and debug through traces. codæ proposes a similar move one abstraction level up: humans inspect the contract; agents compile it into implementation. In VibeLoom, the artifact parser is the frontend, the contract graph is the intermediate representation, traces are source maps, and generated code targets a platform contract such as AWS, GCP, Cloudflare, or a local runtime. This is an analogy, not a proof — a Rust compiler is deterministic, agentic generation is not — but it clarifies the desired control surface and the toolchain that will earn it.

This is what we mean by contract-driven agentic engineering: treating the spec stack not as documentation around the code, but as the contract the code is generated to satisfy. We call the discipline codæ.
