codæ

Contract-driven agentic engineering for dark-factory AI coding.

The end-state of AI coding is not autocomplete, pair programming, or faster pull requests. It is a dark factory: contract in, production system out. Humans govern intent and constraints. Orchestrated agents derive, generate, verify, repair, and regenerate the implementation. By early 2026 the pattern is no longer aspirational — it has begun to ship in pioneering organizations.

Today, the factory does not stay dark. Agents produce code at machine speed but do not reliably preserve meaning across long-running systems. The visible failure modes are AI slop, semantic drift, and comprehension debt. The structural blocker is coherence. codæ proposes the missing control surface: a human-mendable, machine-checkable contract made from mutually-derived specs and a graph that ties them together.

§1 — The destinationSoftware wants a dark factory.

AI coding is usually described as assistance: autocomplete, chat, pair programming, faster pull requests. That is the transitional form. The real destination is production-system synthesis: a human-approved contract enters the system, and a production system comes out.

Contract in. Production system out.

— the dark-factory target

A dark factory does not mean humans disappear. It means humans leave the implementation floor. They govern the contract — intent, product behavior, domain rules, architectural constraints, operational requirements, tradeoffs. Agents operate the factory: deriving artifacts, writing code, generating tests, configuring infrastructure, running checks, diagnosing failures, regenerating outputs.

The dark-factory loop. Humans maintain the contract. Agents operate the factory. Generated implementation is an output, not the primary maintenance surface. Drift returns to the contract — never to the factory floor.

The pattern is already shipping in pioneering organizations. In February 2026, Spotify's co-CEO confirmed the company's best engineers had not written a line of code since December — they were merging hundreds of agent-authored pull requests per month through Spotify's internal coding-agent platform, Honk.17 Two weeks later, BCG Platinion's Dark Software Factory report named the threshold explicitly: "as few as three engineers can run a software factory where humans no longer write code… The moat is not the code. The moat is the specification and the scenario architecture that validates it."18 Sequoia, in their January 2026 essay declaring the practical AGI year, named the underlying capability shift: coding agents that plan, use tools, maintain state, and loop through attempts until success.19 Demis Hassabis describes the same shift from the model side in his 2026 Y Combinator talk on agents and AGI: scientific-research-grade autonomy at increasingly long horizons.24

"You have to be in charge of the aesthetics, the judgment, the taste, and the oversight. People have to be in charge of this spec, this plan."

— Andrej Karpathy, "From Vibe Coding to Agentic Engineering," Sequoia AI Ascent 202520

The economic case writes itself. The industry-promised 10× to 100× productivity gain from agentic coding lives in exactly one place — the dark factory. The moment humans have to step back onto the implementation floor to repair what the agent built, that gain collapses into inspection of machine-volume output. Reading 100,000 lines to safely change 100 isn't a 100× operation. It's barely 1×.

codæ commits to dark-factory coding as a multi-year trajectory, not a v0.3 promise. Today's agents are not yet trustworthy enough to leave alone with the code. The destination is real; the path to it is the rest of this manifesto.

§2 — The contractThe control surface that holds the factory together.

A prompt cannot govern a dark factory. A codebase is too large to be the human control surface. A requirements document is too weak if agents can ignore it. The missing object is a contract — authoritative enough to govern generation, structured enough for agents to consume, and small enough for humans to mend.

Definition

A codæ contract is the authoritative control surface of an agentic engineering system: human-mendable, agent-legible, machine-checkable, traceable end-to-end from intent to running code.

A contract is not documentation, a prompt, a requirements file, or annotations on generated code. None of those govern. Only a contract does.

A contract has four parts. Specs are the atoms. The graph is the structure. Obligations and checks make it load-bearing.

Specs

The atoms. Typed artifacts each carrying one obligation: a requirement, a capability, a flow, an interface, an invariant, a decision, an acceptance criterion, an operational rule.

Graph

The structure. Typed edges connecting specs — derivation, refinement, satisfaction, conflict, traceability.

Obligations

The force. What every generated artifact must satisfy to count as a faithful realization of the contract.

Checks

The enforcement. Structural, mechanical, and semantic verifications that detect contract violations before they enter the working tree.

After the contract exists, the primary noun in every conversation is contract, not specs. Specs are building blocks; the contract is what holds the dark factory together.

§3 — The paradigmcodæ is contract-driven agentic engineering.

codæ names the discipline of building production systems through intelligently orchestrated coding agents governed by a contract. The contract is not documentation around the code. It is the source of truth the code is generated to satisfy.

codæ makes dark-factory coding possible by moving human control from code to contract.

— codæ thesis

In a contract-driven agentic system, agents do not merely receive a task. They inherit a contract, derive missing artifacts from it, implement against it, verify outputs against it, and report unresolved contradictions back into it. Humans do not repair the factory by spelunking through generated implementation. They mend the contract and let the factory regenerate.

The pattern is already taking primitive shape inside today's coding agents. Anthropic's own Claude Code best-practices guidance describes the entry-level case: "Claude doesn't really have memory. The main way we share state across sessions or across our team is this CLAUDE.md file."21 A single markdown file is the proto-contract. codæ is the structured generalization: not one file, but a tiered contract graph; not implicit guidance, but typed obligations and checks.

One contract

The maintained source of truth. Generated code, tests, infrastructure, and traces are downstream artifacts subordinate to it.

Many specs

Atomic obligations expressing requirements, domain meaning, interfaces, behaviors, constraints, and decisions at the right level of abstraction.

Many agents

Specialized roles — derive, implement, test, inspect, repair, refactor, deploy, observe, explain — orchestrated against the same contract.

Many checks

Structural, mechanical, and semantic verifications that continuously test whether generated artifacts satisfy the contract.

From spec-driven to contract-driven

codæ is adjacent to spec-driven development, but it is a step beyond. The 2026 SDD taxonomy15 places existing approaches at three rigor levels: spec-first (specs guide, then drift), spec-anchored (specs and code co-evolve with enforcement), spec-as-source (specs alone are edited; code is regenerated). All three are progress over prompt-only generation. Tools like AWS Kiro25, GitHub Spec Kit, and BMAD live in this band.

codæ is the next level: contract-driven. Not one spec for one file or one feature, but a multi-tier, mutually-derived, graph-tied, drift-detecting contract that governs the whole lifecycle. Spec-driven asks how to make specs better inputs to generation. Contract-driven asks how to make a contract the durable control surface of the lifecycle. Same impulse, larger surface, longer arc.

§4 — The blockerCoherence fails, and local fixes can't restore it.

The central obstacle to dark-factory AI coding is not syntax, boilerplate, or local code generation. Agents are already useful for bounded tasks. The gating constraint is coherence: preserving intent, architecture, domain meaning, constraints, and behavior across long-running, multi-component, multi-agent work.

When coherence fails, the symptoms have names:

  • Semantic drift — outputs progressively diverge from original task intent while remaining plausible and syntactically valid.
  • AI slop1 — code that looks reasonable, passes review-by-glance, and accumulates faster than reviewers can absorb.
  • Comprehension debt2 — the codebase appears clean, but no human or incoming agent understands what it is doing or why.

These are not the destination. They are the evidence that the current factory has no durable control surface — and the team-performance literature converges with the academic findings. Nicole Forsgren — DORA-research lead and co-author of Accelerate — frames the team-level corollary in her 2026 Pragmatic Engineer talk on leading engineering teams in the AI era: high-performing teams are the ones that systematize what was previously tacit context.22

SlopCodeBench3 makes the failure mechanical: 20 problems × 93 checkpoints × 11 models, instrumented to measure how agent code degrades when agents iteratively extend their own prior code under evolving requirements. No agent solves a whole problem end-to-end. Agent code runs 2.2× more verbose than comparable open-source Python repositories.

The same pattern appears in live code. Liu et al.13 tracked 302.6k verified AI-authored commits across 6,299 repositories and identified 484,366 introduced issues; 22.7% survive at latest revision. The social cost has been characterized too: Baltes, Cheong, and Treude1 frame the result as a software-commons problem14 — generation gains for one developer become review and maintenance costs for everyone else. The mechanism upstream of all of this is documented in Chroma's Context Rot report4: every frontier model becomes unreliable as input length grows; SWE Context Bench11 adds the corollary — context quality, not quantity, is what improves agent accuracy and cost.

AI amplifies the quality of the engineering system it operates within.

— DORA 2025 report on AI-assisted development6

Organizations with mature systems get leverage. Organizations with fragmented systems get accelerated drift. A dark factory cannot depend on tacit human memory to repair that gap.

Why local fixes fail

The default response to drift is local steering: better prompts, sharper instructions, more elaborate rules files, stricter reviewer checklists. This works for one run. It dies on the next agent, the next session, the next contributor, the next context window.

Chat history is not memory. A prompt is not authority. The next agent does not reliably inherit what the last one was told. Every cycle re-derives the system from partial context, and the durable artifact becomes the codebase itself — too large for any human or agent to re-internalize from scratch. Karpathy, the same talk that named "agentic engineering," concedes the point: "agent workflows need docs, memory, project files, rules, tests, and clear feedback loops."20 That sentence is the requirement spec for a contract. Matt Pocock makes the complementary point at AI Engineer 2026: software fundamentals — explicit interfaces, durable contracts, named invariants — matter more in the agentic era, not less.23

Code review is not the dark-factory control system either. If humans must repeatedly enter generated implementation to restore coherence, the factory is not dark — and the promised speedup collapses into manual inspection of machine-volume output. The cumulative cost is measurable: an Anthropic study cited by O'Reilly7 finds developers using AI assistance score 17% lower on comprehension after equivalent tasks, with the largest decline in debugging.

Making code cheap to generate doesn't make understanding cheap to skip. The comprehension work is the job.

— Addy Osmani, O'Reilly Radar, Apr 20267

Drift, then, is not a vague quality problem. With a contract in place, it becomes a concrete contract violation: detectable, attributable, localizable, and repairable at the contract boundary, before humans are pulled back onto the floor. The fix has to be more durable than chat and smaller than code. It has to be a maintained contract that agents can consume and humans can repair.

§5 — The mendable surfaceMove human control above implementation.

The dark factory stays dark only while humans stay above the code. The load-bearing question is not how many lines a human can review. It is how many meaningful items a human can hold in the affected review cut — code-level (files, classes, functions, branches, tests, integrations, dependency edges) versus contract-level (capabilities, constraints, requirements, flows, bounded contexts, interfaces, behaviors, decisions, obligations).

Code grows roughly as features × accumulation: every branch, retry path, glue layer, integration, edge case adds items. Human comprehension does not scale linearly with that growth. The working-memory ceiling is hard — humans plateau around 7±2 elements; cognitive-load research formalizes the rest. Above the ceiling, code remains readable line by line but opaque as a system.

The contract has a different shape. It captures what the system is, what must remain true, and what generated artifacts must satisfy. A small set of concepts at the right abstraction level can govern a much larger set of implementation paths. That is why the contract — not the code — is the human-mendable surface.

Cognitive surface, to scale. A 108K-line system lies far above any human comprehension ceiling. The contract governing it — intent, requirements, structure, behavior, config — is roughly 24% of the code volume and fits below the ceiling. Humans mend the contract. Agents extend the implementation.8

One empirical anchor (using lines as a coarse proxy for items): Vasilopoulos's 2026 field study reports a 108,000-line C# distributed system governed by ~660 lines of hot-memory constitution, 19 specialized agents (~9,300 lines), and 34 on-demand specification documents (~16,250 lines), across 283 development sessions.8 Even by the cruder line-based proxy, the contract is a fraction of the code and is sufficient to keep agents pattern-adherent at scale.

Cognitive-load-aware refactoring research9 confirms the principle from a different angle. Across 974 MBPP programs, 5,000 APPS programs, and a human study of 20 programmers: structures aligned to working-memory limits reduce failures by 54–71% versus unconstrained prompting and improve comprehension scores by 17–31% across multiple measures. Structure that fits the cognitive surface is not decoration. It is a performance lever.

"Treating project documentation as infrastructure rather than artifact: living specifications that AI agents depend on to produce correct, convention-adherent code."

— Vasilopoulos, Codified Context, Feb 20268

§6 — The durable objectThe contract is memory. The contract is eval.

Once the contract exists, it does more than describe the system. It becomes the durable memory the next agent inherits and the eval surface every generated artifact is checked against. Both are prerequisites for the dark factory.

The contract as long-term memory

When chat is cheap and context is rotting, the only persistent representation of "what this system is supposed to be" is the contract. Anthropic's 2026 Agentic Coding Trends Report10 puts it bluntly: engineers use AI in roughly 60% of work but can fully delegate only 0–20%. The constraint isn't model capability. It's context.

The gap isn't capability. The gap is that fully delegating a task requires the agent to have the right context to complete it.

— Anthropic, 2026 Agentic Coding Trends Report10

SWE Context Bench11 tests the same mechanism on 1,100 base tasks across 51 repositories and 9 languages. Correctly selected, summarized context — distilled intent and structure — improves resolution accuracy and reduces runtime/token cost. Unfiltered or wrongly-selected context provides negative benefit. The contract is curated, summarized, high-signal context, durable across agents and sessions.

The contract as eval signal

The same contract checks what agents produce. Generated specs, code, tests, migrations, infrastructure, traces — every downstream artifact can be verified structurally (does it derive from the right upstream obligations?) and semantically (does it preserve the intended meaning?).

REA-Coder12 tested the shape directly: align requirements before generation, verify after, iterate on misalignments. Across 4 LLMs and 5 benchmarks, the result was 7.93% to 30.25% Pass@1 improvement. The binding constraint on code-generation quality is not model capability. It is requirement understanding. Fix the contract; the code follows.

That does not prove contract-driven agentic engineering eliminates drift end-to-end. It supports the mechanism: align against a contract before generation, then verify against it after. Drift becomes a contract violation — detectable, attributable, localizable, and repairable at the contract boundary before humans are forced back into implementation.

§7 — The ladderToward a decidable contract.

codæ is an hommage to Bertrand Meyer's Design by Contract16, not an equivalence. Meyer's discipline made obligations explicit between software elements through preconditions, postconditions, and invariants — and crucially made many of those obligations decidable: boolean-checkable at runtime, sound for the property they encoded. Contract-driven agentic engineering inherits the discipline of explicit obligations and the principle that downstream artifacts must satisfy upstream contracts. It does not yet inherit full decidability. The trajectory is to climb toward it.

Rung 1

Semantic eval

Heuristic. Requirement alignment, intent preservation, architectural fit, omitted obligations, hidden conflicts, explanation quality. Agent-judged where machines can't yet decide. This is where most of the contract is checked today.

Rung 2

Mechanical runners

Validation runners — type checks, tests, linters, migrations, policy checks, infrastructure validation, interface conformance, smoke tests, deployment probes. Project-defined; orchestrator-invoked.

Rung 3

Structural checks

Decidable. IDs, schema validity, contract-graph edges, coverage, traceability, artifact provenance, dependency consistency, absence of unresolved contradictions. The engine performs these without an LLM.

The climb goes upward. Each release should promote checks toward decidability — heuristic dimensions become mechanical runners; mechanical runners become structural rules. The decidable share of the contract grows as the engine matures.

The compiler was software's first dark factory.

Software has done this climb before — one abstraction level down. We used to inspect generated machine code. Now we inspect source, trust the toolchain, test the result, debug through traces. The compiler is the canonical dark factory: humans write source, the toolchain compiles, nobody reads the assembly. We trust it because its contract is decidable.

codæ proposes the same move one level up: humans inspect the contract; agents compile it into implementation. The artifact parser is the frontend, the contract graph is the intermediate representation, traces are source maps, and generated code targets a platform contract such as AWS, GCP, Cloudflare, or a local runtime. The analogy is not a proof — a compiler is deterministic, agentic generation is not — but it clarifies the desired control surface and the toolchain that earns it. The long-term ambition is the dream Meyer's discipline pointed at: formally verifiable software, this time at contract scope rather than routine scope. That destination is years away. The ladder is the climb.

§8 — The betGenerated implementation is not the source of truth.

The choice underneath codæ is binary, and worth saying out loud.

One option: keep code human-mendable. The agent drafts; the human reviews, edits, ships. Useful — but not a dark factory. The moment humans must repeatedly enter generated implementation to restore intent, architecture, or behavior, the speedup collapses into manual inspection of machine-volume output. Reading 100,000 lines to safely change 100 isn't a 100× operation. It's barely 1×.

The other option: code is generated, regenerated, and treated as downstream infrastructure. The contract is what humans maintain. The contract is what agents satisfy. The contract is what detects drift. The contract is what receives repair. This is the codæ bet.
