Get started · v0.3

Make your first contract in 30 minutes.

Clone the repo, load it as a Skill in Claude Code or Codex, and run one command. Python 3.10+ is the only system requirement — the engine is pure Python with zero runtime dependencies.

Start in vibe mode Vibe is the cold-start path. Begin there even if you'll outgrow it — the upgrade trace is part of how the methodology works.
~5 min read · ~30 min hands-on Source: getting-started.md v0.3

Prerequisites

  • Python 3.10+ — the only system dependency.
  • An agent with a Skill loader — Claude Code or Codex. Both pick up VibeLoom the same way.
  • A folder to try it on — a throwaway directory works for the vibe walkthrough; a real codebase works for the brownfield path.

Install

Clone the repo:

git clone https://github.com/ilya-baimetov/vibeloom.git

Point your agent at the cloned directory as a Skill source. In Claude Code:

> add vibeloom as a Skill source from /path/to/vibeloom/v03

Codex setup is the same shape — point its Skill loader at the same directory. No pip install. No runtime dependencies beyond Python.

First 5 min — bootstrap a vibe project

In an empty directory (or a folder you want to seed):

> /vibeloom init --mode vibe "a personal note-taking app with full-text search and tags"

VibeLoom creates intent.md, system.md (compact), and AGENTS.md. It writes your one-line description into intent.md and asks you to expand. Open the file and add capabilities and constraints in plain English — that's the only real work here.

Then approve:

> /vibeloom approve intent-specs

This writes the first approval trace and unlocks downstream generation.

Next 10 min — generate

> /vibeloom generate

In vibe mode this auto-advances through the compact stack and into code. Expect output that looks roughly like:

✓ generated system.md (compact: 3 components, 2 interfaces)
✓ generated AGENTS.md
✓ generated code (14 files across 3 components in 2 dispatch waves)
✓ all validation runners passed
ℹ status: current; 0 stale, 0 drifted, 0 uncovered

Look at what got generated. Ignore the engine's status report for a second — just open the files and skim them. The whole point of vibe mode is that a small system stays comprehensible.

Next 10 min — read, ship, iterate

If the generated code looks roughly right:

> /vibeloom status

Read the report. If it says current everywhere, ship it. Run the code, see if it does what you wanted.

To change behavior, you have two paths:

  • Change the intent. Edit intent.md, approve it again, generate again. The engine regenerates affected scopes.
  • Edit the code by hand. Fine, but on the next status you'll see drifted for whichever files you touched. Use reconcile code to either bring code back in line with the contract or amend the contract to match what you wrote. Don't ignore drift.

Outgrow vibe — upgrade

After a few weeks of iteration, VibeLoom may surface:

ℹ Vibe limits exceeded:
  - 12 components (vibe recommends ≤ 5)
  - 3 contributors (vibe recommends 1-2)
  - 4 reconciliations in last 30 days
→ Consider: vibeloom init --upgrade --mode <pm|dev|ux|expert>

This is the upgrade prompt. Pick a mode based on who's leading discovery on your team:

  • pm — product-led. PM owns intent + product specs. Best for product-driven teams.
  • dev — tech-led. Dev owns intent + system specs. Best for architecture-first work.
  • ux — design-led. Designer owns intent + UX specs; PM is peer reviewer of generated product specs. Best for design-heavy products. See examples/ux-led-design.md.
  • expert — all approval gates explicit. Best for regulated systems or co-owned design.
One-way. Upgrade is one-way and produces an explicit migration trace. The compact stack expands into the full graph; existing code is import-analyzed against the freshly generated full contract. Plan ~1 hour for the first review pass after upgrade.

I have an existing codebase — brownfield import

Use brownfield import:

> /vibeloom import --mode <mode>

VibeLoom scans the existing code, infers a candidate contract with confidence scores per item, and writes it as draft. You review top-down (intent → product → system) and approve. Existing code is then code-synced or reconciled against the approved contract.

Plan a half-day to a day for the first import + review cycle on a 50K-LOC project. See examples/brownfield-import.md for a worked walkthrough.

When NOT to use VibeLoom

Throwaway prototype? Single-file utility? Weekend demo? Hackathon submission? Prompt-only is faster. The contract overhead pays back when the system has to survive past one development cycle and matter to more than one person. See manifesto §6 for the argument.
