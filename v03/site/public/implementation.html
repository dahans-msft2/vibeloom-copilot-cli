In 60 seconds

VibeLoom is a Skill for Claude Code / Codex plus a deterministic Python engine. The Skill judges and orchestrates; the engine parses, validates, and detects drift. They cooperate through a shared substrate split into a regenerable cache and durable append-only traces. Pure Python, zero runtime dependencies. This page covers the boundaries, the substrate, the engine CLI, approval traces, the contract graph, IDs and frontmatter, trace families, subagent dispatch, install + run, and source layout.

If you're new — start with the methodology page for the why, then come back here for the how.

Skill and engine, one substrate

VibeLoom is delivered as two cooperating layers:

  • The Skill — a prompt-and-policy package that loads automatically inside Claude Code or Codex. It owns the natural-language interface, mode selection, approval pauses, semantic judgment, subagent orchestration, and template materialization.
  • The engine — a deterministic Python package that parses artifacts, validates schemas, builds the contract graph, computes affected sets, plans dispatch waves, and detects structural and lifecycle drift. It makes no semantic judgments and never asks a model for an answer.

They cooperate through a shared substrate at .vibeloom/, split into a regenerable cache and durable append-only traces (next section). The engine writes state into both; the Skill reads them, makes decisions, generates content, and invokes the engine again on the result. There is no other channel between them.

Why split it. Anything load-bearing — hash diffs, derivation walks, schema validation, dispatch planning — needs to be deterministic and auditable. Anything that requires judgment — semantic eval, mode selection, conflict resolution — needs a model. Mixing the two produces software that's neither.

Cache + traces

The shared substrate at .vibeloom/ is split deliberately:

  • Cache (.vibeloom/cache/) — regenerable state. The contract graph, status snapshots, indices. If deleted, the engine rebuilds from artifacts and traces.
  • Traces (.vibeloom/traces/) — durable provenance. Append-oriented JSONL streams (with the ID registry as a structured exception). Traces are never silently regenerated; missing traces degrade governance integrity and require explicit re-baselining.

This split is the key to drift detection: the cache is whatever the engine currently knows; the traces are the immutable record of what was approved, generated, evaluated, and decided. Drift is the gap between current state and the basis recorded in traces.

The Skill

The Skill is a single SKILL.md file plus a references/ tree of load-on-demand guides. It's loaded automatically by Claude Code and Codex when you invoke /vibeloom or $vibeloom.

The Skill's responsibilities:

  • Receive operations (init, generate, review, etc.) and parse them into a target tier and scope.
  • Load the correct subset of references/ for the operation — never load everything.
  • Materialize templates from assets/ when generating new artifacts.
  • Invoke the engine for parsing, eval, staleness, dispatch planning, and status.
  • Run heuristic semantic eval (the verification ladder's top tier — see methodology) against items the engine flagged as in scope.
  • Dispatch scoped subagents in waves for code generation, with bounded load sets (see Subagent dispatch).
  • Pause at every approval gate the current mode requires; never bypass one.

The Skill is intentionally short — most of the operational detail lives in the methodology and in narrowly scoped references that are loaded only when relevant. This keeps the always-resident context small.

The engine

The engine is a pure Python package with zero runtime dependencies beyond Python 3.10+ (the YAML frontmatter parser is custom, minimal, and shipped in-tree). No pip install is required to use it from the Skill.

The engine's responsibilities, in scope and out:

  • In scope: parsing artifacts; assigning and validating stable IDs; validating frontmatter and schemas; building and querying the contract graph; computing affected sets; reading and writing trace files for deterministic events; planning dispatch waves; computing status across the lifecycle / freshness / coverage axes.
  • Out of scope: deciding what items mean; deciding which fix direction is correct; choosing modes; talking to users.

All engine commands emit JSON on stdout. Non-zero exit codes indicate blocking findings or errors. The Skill consumes the JSON and renders human-facing output.

Engine CLI

The deterministic surface is exposed through these CLI commands.

parse        --repo <path>                       # Parse all artifacts; emit JSON inventory
graph        --repo <path>                       # Build + persist .vibeloom/cache/contract-graph.json
eval         --repo <path> [--target <tier>]     # Run structural checks; non-zero exit on blockers
affected     --repo <path> --ids <IDs...>        # Compute affected set from changed item IDs
staleness    --repo <path>                       # Per-item hash diff vs approval traces; forward DAG walk
detect-edits --repo <path>                       # mtime fast-filter + per-item hash confirmation
dispatch     --repo <path> --affected <IDs>      # Build dispatch plan with wave assembly
status       --repo <path>                       # Emit + persist status across all axes

Without install, prefix every invocation with PYTHONPATH=<skill-root>/engine. With pip install -e engine, a shorter vibeloom-engine binary lands on PATH.

Approval traces and drift detection

The approval trace is the load-bearing substrate for drift detection.

When the user (or the agent, in delegated mode) approves a contract tier, the engine appends an approval trace to .vibeloom/traces/approvals.jsonl. Each entry records:

  • Which tier was approved (the approval unit).
  • Per-item content fingerprints (SHA-256 canonical hashes — normalized so renames surface as remove + add and non-semantic edits like whitespace don't churn).
  • Per-artifact hashes alongside the items.
  • Approval mode (user or delegated), run ID, timestamp, author.

The trace is append-only and never regenerated. Future passes compare current per-item hashes against the most recent approval trace; the diff is the set of changed items.

Direct-edit detection uses the same trace via a two-tier compare: filesystem mtime first (fast), then per-item hash (precise). If any item is added, removed, or modified outside the normal flow, the artifact auto-reopens to draft. Whitespace-only edits leave the artifact approved.

Approval traces also enable upgrade migrations (vibe → full mode) and any future replays from history.

The contract graph

The graph is built by the engine from the entire artifact set. Nodes are IDed semantic items (entities); edges are typed derives_from relations read out of artifact frontmatter. The graph is a DAG — cycles are forbidden, and only capability and constraint are valid roots.

In v0.3, the contract graph is shaped as a knowledge graph: instantiated ontology only. Provenance lives in traces (see Approval traces and Trace families); a future release may promote provenance into graph form (see roadmap CGKG-B).

Two operations compute on the graph:

  • Affected set — given a set of changed item IDs, walk forward through derives_from to collect every reachable downstream item. Unit of work for generate and reconcile.
  • Stale set — combination of: items modified since the most recent approval trace, items removed since, and the affected-set walk forward from both. Stale items map back to their owning artifacts to produce the stale-artifact set.

The graph is persisted to .vibeloom/cache/contract-graph.json. It's regenerated on demand and is safe to delete — the next pass rebuilds it from artifacts.

IDs and frontmatter

Every first-class item carries a stable, prefixed, fixed-width ID. Examples across the contract stack:

TierFamilyItem type
intent-specsCAPcapability
intent-specsCST, DEFconstraint, default
product-specsFR, NFRrequirement
product-specsEPIC, FLOW, STORY, ACCuser story map
product-specsBC, AGG, ENT, VO, INV, TERMdomain model
ux-specsVIEW, INT, UXC, MOCKUX surfaces
system-specsCONT, CMP, IF, DEP, BEHsystem structure

Each artifact carries YAML frontmatter recording lifecycle status, mode metadata, and per-item derives_from references. Containers carry a required layer field (presentation / application / domain / infrastructure) that drives layer-aware generation rules.

A typical container fragment:

---
type: container
status: approved
container: notes-api
layer: application
---

A typical domain-layer component fragment:

---
type: component
status: approved
approval_mode: user
container: search
component: notes-search
---

## IF-0014 · search(query, tags) → results
derives_from: [FR-0007, STORY-0023]
behavior: Returns results matching all tags AND any token in query, ranked by recency.

## DEP-0002 · depends_on: index-store
derives_from: [BC-0003]
interface: IF-0011 (read)

## BEH-0019 · empty-query short-circuit
derives_from: [STORY-0023]
expected: Empty query with no tags returns no results without touching the index.

A typical decision trace entry (the record_type classifies which contract tier the decision primarily affects):

{
  "trace_id": "DEC-20260512-0007",
  "kind": "decision",
  "record_type": "ADR",
  "load_bearing": true,
  "affects": ["BC-0008", "FR-0042"],
  "topic": "tax-calculation-strategy",
  "author": "ilya@vibeloom.ai",
  "payload": "Selected progressive bracket calculation. Rejected: flat-rate (oversimplifies state-level variance), per-jurisdiction lookup (too brittle to maintain)."
}

The frontmatter parser is strict — required fields are validated by the engine; unknown fields are flagged. Layer-aware constraints (e.g. hosted_bounded_contexts must be empty in non-domain components) are checked structurally.

Trace families

Traces are append-oriented provenance. Each family has its own JSONL stream (the ID registry is the structured exception). Schemas are designed so the relationships they capture can be promoted to graph form in a future release without information loss (see roadmap CGKG-B).

FamilyCaptures
approvalWho/what approved which contract basis, with per-item content fingerprints
generationWhat task generated which artifact from which basis (output_item_ids close the provenance loop)
evalWhat checks ran and what findings resulted (per-finding item_id captured)
code-syncSource-map-shaped: code paths/hashes ↔ contract IDs ↔ validation evidence
decisionHuman-authored decision history. record_type classifies as IDR (intent-specs), PDR (product-specs), UDR (ux-specs), ADR (system-specs), or general (process / methodology / operational decisions that don't change the contract). load_bearing + affects identify the active subset informing future generation.
importBrownfield aggregate evidence + confidence; per-candidate evidence in resulting draft artifacts

Full schemas with fields and examples: see canonical implementation §8.

Subagent dispatch

Code generation runs as scoped subagent waves planned by the engine and orchestrated by the Skill. The engine returns a dispatch plan; the Skill executes it.

  • Dispatch plan — engine output for a generation run: an ordered list of waves, each containing component-shaped scopes with their owned paths, allowed read paths, task template, and dependencies on other scopes.
  • Wave assembly — two scopes share a wave only if their owned paths are disjoint (writes can't collide). Scope B is in a later wave than scope A only if B's derives_from references items owned by A. Reconciliation tasks always run as singletons.
  • Parallel semantics — within a wave, subagents run concurrently; the orchestrator awaits all results, then applies patches sequentially in scope-id order. Validation runners per task run inside the subagent's staging dir before the patch reaches the working tree.
  • Subagent task header — the orchestrator-to-subagent contract: task ID, run ID, wave ID, template ID + version, scope, load-set refs, foreign refs, allowed read/write paths, validation contract, result shape ID. This is what makes prompts mendable.
  • Load set — what each subagent receives: baseline (root config + defaults) + owned scope + foreign slices (interface contracts only, not internals) + relevant context. Typical loads sit at 6–12K tokens.
  • Late-fetch — a single approved task-local additional context slice that a subagent may request once if it discovers a narrow missing dependency. Cap is one re-invocation per task; exceeding it surfaces a finding and exits.

The orchestrator validates cross-scope consistency after each wave: do interfaces match? do dependencies resolve? are BDD scenarios still satisfied? Failures reopen affected components for another pass.

Install + Quickstart

Zero install. Python 3.10+ is the only system requirement. From the Skill's perspective, the engine is invoked via:

PYTHONPATH=<skill-root>/engine python3 -m vibeloom_engine <command> --repo <target-repo>

Optional, for CLI-only direct use: cd <skill-root>/engine && pip install -e . lands the vibeloom-engine binary on PATH.

Open a project directory in Claude Code or Codex. The Skill is picked up automatically. A vibe-mode session looks like:

$ /vibeloom init --mode vibe "a CLI for journaling with tags"
✓ Created intent.md (draft) — capabilities + constraints extracted
✓ Created defaults.md (draft) — defaults derived from intent
✓ Eval intent-specs — no blocking findings
→ Next: /vibeloom approve intent-specs

$ /vibeloom approve intent-specs
✓ intent-specs approved (mode=user) · approval trace emitted
✓ Auto-advanced compact system-specs
✓ Generated context (AGENTS.md, CLAUDE.md)
✓ Generated code in dispatch wave

$ /vibeloom status
✅ intent-specs    approved (clean)
✅ system-specs    approved (clean, delegated)
✅ context         current
✅ code            current

The compact vibe-mode layout is much smaller — just intent + defaults + flat system + an AGENTS.md + a traces directory holding approvals + decisions. No graph cache, no code-sync. (See methodology for the design rationale.)

Testing

The engine has tests covering parser, graph, eval, staleness, dispatch planning, and CLI. pytest is the only dev dependency.

cd engine
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/pytest

The Skill is, by nature, harder to unit-test — it runs inside an LLM. Behavior is verified end-to-end against the canonical operations on a set of seed projects.
