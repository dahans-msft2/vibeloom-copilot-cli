VibeLoom v0.3 is a Skill for Claude Code / Codex plus a deterministic Python engine. The Skill judges and orchestrates; the engine parses, validates, and detects drift. They cooperate through one shared substrate at .vibeloom/state/. Pure Python, zero runtime dependencies, with structural checks and a tested engine surface. This page covers the boundaries, the engine CLI, the snapshot algorithm, the contract graph, IDs and frontmatter, subagent dispatch, and how to install + run.

If you're new — start with the methodology page for the why, then come back here for the how.

Skill and engine, one substrate

VibeLoom v0.3 is delivered as two cooperating layers:

  • The Skill — a prompt-and-policy package that loads automatically inside Claude Code or Codex. It owns the natural-language interface, mode selection, approval pauses, semantic judgment, subagent orchestration, and template materialization.
  • The engine — a deterministic Python package (vibeloom-engine 0.2.0) that parses artifacts, validates schemas, builds the derivation graph, computes affected sets, and detects structural and lifecycle drift. It makes no semantic judgments and never asks a model for an answer.

They cooperate through a single shared substrate: .vibeloom/state/. The engine writes contract-graph.json, status.json, and approved_snapshots/. The Skill reads them, makes decisions, generates content, and invokes the engine again on the result. There is no other channel between them.

Why split it. Anything load-bearing — hash diffs, derivation walks, schema validation — needs to be deterministic and auditable. Anything that requires judgment — semantic eval, mode selection, conflict resolution — needs a model. Mixing the two produces software that's neither.

The Skill

The Skill is a single SKILL.md file plus a references/ tree of load-on-demand guides. It's loaded automatically by Claude Code and Codex when you invoke /vibeloom or $vibeloom.

The Skill's responsibilities:

  • Receive operations (init, generate, review, etc.) and parse them into a target tier and scope.
  • Load the correct subset of references/ for the operation — never load everything.
  • Materialize templates from assets/ when generating new artifacts.
  • Invoke the engine via python -m vibeloom_engine for parsing, eval, staleness, and status.
  • Run the four-dimension semantic eval against the items the engine flagged as in scope.
  • Dispatch scoped subagents in waves for code generation, with bounded load sets.
  • Pause at every approval gate the current mode requires; never bypass one.

The Skill is intentionally short — most of the operational detail lives in the methodology and in narrowly scoped references that are loaded only when relevant. This keeps the always-resident context small.

The engine

vibeloom-engine 0.2.0 is a pure Python package. Including its custom-built minimal YAML frontmatter parser, it has zero runtime dependencies beyond Python 3.10+. No pip install is required to use it from the Skill — invoke via python -m vibeloom_engine.

The engine's responsibilities, in scope and out:

  • In scope: parsing artifacts; assigning and validating stable IDs; validating frontmatter and schemas; building and querying the contract graph; computing affected sets; capturing and comparing approved-state snapshots; emitting status snapshots.
  • Out of scope: deciding what items mean; deciding which fix direction is correct; choosing modes; talking to users.

All engine commands emit JSON on stdout. Non-zero exit codes indicate blocking findings or errors. The Skill consumes the JSON and renders human-facing output.

Engine CLI

The deterministic surface is exposed through these CLI commands.

parse       --repo <path>                       # Parse all artifacts; emit JSON inventory
graph       --repo <path>                       # Build + persist .vibeloom/state/contract-graph.json
eval        --repo <path> [--target <tier>]     # Run structural checks; non-zero exit on blockers
affected    --repo <path> --ids <IDs...>        # Compute affected set from changed item IDs
staleness   --repo <path>                       # Per-item hash diff + forward DAG walk
detect-edits --repo <path>                      # mtime fast-filter + per-item hash confirmation
status      --repo <path>                       # Emit + persist status snapshot

Without install, prefix every invocation with PYTHONPATH=<skill-root>/engine. With pip install -e engine, a shorter vibeloom-engine binary lands on PATH.

Approved-state snapshot

The snapshot is the single most important data structure in v0.3 — it's what makes drift detection enforceable rather than aspirational.

When the user (or the agent, in delegated mode) approves a contract tier, the engine captures, per artifact:

  • The artifact's filesystem mtime.
  • For each item parsed out of the artifact, its SHA-256 canonical hash — normalized so renames surface as remove+add and non-semantic edits (whitespace, comment-only changes) don't churn.

The snapshot is preserved across rebuilds. It is dropped only when the artifact transitions back to draft. This is what enables the staleness pass — the engine compares current per-item hashes against the snapshot, and the diff is the set of changed items.

Direct-edit detection uses the same snapshot via a two-tier compare: filesystem mtime first (fast), then per-item hash (precise). If any item is added, removed, or modified, the artifact auto-reopens to draft. Whitespace-only edits leave the artifact approved.

The contract graph

The graph is built by the engine from the entire artifact set. Nodes are items (with stable IDs); edges are typed derivation relationships read out of derives_from frontmatter. The graph is a DAG — cycles are forbidden, and only capability and constraint are valid roots.

Two operations compute on the graph:

  • Affected set — given a set of changed item IDs, walk forward through derives_from to collect every reachable downstream item. This is the unit of work for generate and reconcile.
  • Stale set — combination of: items modified since the snapshot, items removed since the snapshot, and the affected-set walk forward from both. Stale items map back to their owning artifacts to produce the stale-artifact set.

The graph is persisted to .vibeloom/state/contract-graph.json. It's regenerated on demand and is safe to delete — the next pass rebuilds it.

IDs and frontmatter

Every first-class item carries a stable, prefixed, fixed-width ID. There are 30+ ID families covering the contract stack — a few examples:

TierFamilyItem type
intent-specsCAP-####capability
intent-specsCST-####constraint
product-specsFR-####functional requirement
product-specsSTORY-####user story
product-specsBC-####bounded context
product-specsTERM-####ubiquitous-language term
system-specsCMP-####component
system-specsIF-####typed interface
system-specsBEH-####component behavior

Each artifact carries YAML frontmatter recording lifecycle status, mode metadata, and per-item derives_from references. Containers carry a required layer field (presentation / application / domain / infrastructure) that drives layer-aware generation rules. A typical container fragment:

---
type: container
status: approved
container: notes-api
layer: application
---

And a typical domain-layer component fragment:

---
type: component
status: approved
approval_mode: user
container: search
component: notes-search
---

## IF-0014 · search(query, tags) → results
derives_from: [FR-0007, STORY-0023]
behavior: Returns the top 50 results matching all tags AND any token in query, ranked by recency.

## DEP-0002 · depends_on: index-store
derives_from: [BC-0003]
interface: IF-0011 (read)

## BEH-0019 · empty-query short-circuit
derives_from: [STORY-0023]
expected: An empty query with no tags returns 0 results without touching the index.

The frontmatter parser is strict — required fields are validated by the engine, and unknown fields are flagged. This keeps the graph buildable without ambiguity. Layer-aware constraints (e.g. hosted_bounded_contexts must be empty in non-domain components) are checked structurally.

Subagent dispatch

Code generation runs as scoped subagent waves. The Skill computes the affected component set from the engine's affected-set output, then dispatches one subagent per component.

  • Wave — a set of subagent tasks whose prerequisites are satisfied and whose write scopes are mutually compatible. Writes are disjoint by directory ownership declared in component.md, so subagents within a wave cannot collide.
  • Load set — what each subagent receives: baseline (root config + defaults) + owned scope + a referenced foreign slice (only the IF-#### contracts of dependencies, not their internals) + relevant context. Typical loads sit at 6-12K tokens.
  • Late-fetch — a single approved task-local additional context slice that a subagent may request once if it discovers a narrow missing dependency. Cap is one re-invocation per task; exceeding it surfaces a finding and exits.
  • Spot reads — read-only access to specific items outside the load set, for verification only. Never used to expand write scope.

The orchestrator validates cross-scope consistency after each wave: do the IFs match? do the dependencies resolve? are the BDD scenarios still satisfied? Failures in this validation reopen the affected components for another pass.

Install

Zero install. Python 3.10+ is the only system requirement. From the Skill's perspective, the engine is invoked via:

PYTHONPATH=<skill-root>/engine python3 -m vibeloom_engine <command> --repo <target-repo>

Optional, for CLI-only direct use:

cd <skill-root>/engine
pip install -e .
vibeloom-engine --version
# vibeloom-engine 0.2.0

Quickstart

Open a project directory in Claude Code or Codex. The Skill is picked up automatically.

$ /vibeloom init --mode vibe "a CLI for journaling with tags"

✓ Created intent.md (draft, 5 capabilities, 2 constraints)
✓ Created defaults.md (draft, 7 defaults derived from intent)
✓ Eval intent-specs: 0 blocking, 0 advisory
→ Next: /vibeloom approve intent-specs

$ /vibeloom approve intent-specs
✓ intent-specs approved (mode=user, snapshot captured)
✓ Auto-advanced compact system-specs (3 components)
✓ Generated context: AGENTS.md, CLAUDE.md
✓ Generated code: 9 files in 1 dispatch wave

$ /vibeloom status
✅ intent-specs    approved (clean)
✅ system-specs    approved (clean, delegated)
✅ context         current
✅ code            current — 9 files, 3 components

Testing

The engine has 25 tests covering parser, graph, eval, staleness, and CLI. pytest is the only dev dependency.

cd engine
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/pytest
# 25 passed

The Skill is, by nature, harder to unit-test — it runs inside an LLM. Behavior is verified end-to-end against the seven canonical operations on a set of seed projects.
