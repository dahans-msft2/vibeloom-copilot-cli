Methodology · v0.3

The contract-driven methodology for AI-coded projects.

VibeLoom turns intent into a tiered, version-controlled contract — durable, derivation-aware, and treated as both source of truth and eval system. This page explains the principles, the artifacts, the operations, and the invariants that hold the stack together.

Core thesis AI-generated systems need a governed contract stack, not a longer prompt. The stack doubles as the eval surface that keeps downstream artifacts coherent across every generation, contributor, and revision.

Principles

VibeLoom rests on a small set of load-bearing ideas. Everything else — artifacts, modes, operations, engine — is mechanism in service of these.

  1. Live contract, not stale specs. The system is defined by a living contract stack; specs are graph-nodes with derivation edges, not one-off planning documents.
  2. Contract is the eval surface. The same upstream items that drive generation also serve as the basis against which downstream output is checked.
  3. Human-mendable review surface. Humans review affected contract cuts, approval packets, and reconciliation choices — not full generated code.
  4. Traceability by ID. Every governed semantic item carries a stable ID and an explicit derivation basis.
  5. Contract aspires toward decidability. Eval operates on a verification ladder (decidable / mechanical / heuristic). The trajectory: promote checks upward as the engine matures.

When to use VibeLoom

Use VibeLoom when:

  • The system must survive more than one generation step or contributor.
  • Product, domain, UX, or architecture decisions matter.
  • Drift would be expensive or dangerous.
  • You need traceability from intent to implementation.

Don't use VibeLoom for throwaway prototypes, single-file utilities, or weekend demos. Heuristic: if the generated code surface is under ~500 LOC and won't survive past one cycle, prompt-only is faster.

Architecture

Working layers stack top to bottom — Contract above Context above Code — and traces run alongside as durable provenance.

  • Contract — governed semantic truth. Has lifecycle state (draft or approved). Only approved items drive downstream generation.
  • Context — active generation guidance derived from approved contract. Not approved like contract; the fix path for bad context is to amend the upstream contract and regenerate.
  • Code — executable output: source, tests, runtime, deployment, migrations. Synchronized and validated, not approved.
  • Traces — durable provenance running parallel. Captures approvals, generation events, eval results, code-sync, decisions, imports. Never silently regenerated from current state.
Important. The context tier means generated execution guidance (configs, behavioral scenarios) — not the LLM's context window. Easy to confuse.

The contract stack

intent → product ⇄ ux → system. Each tier derives from the approved tier above. product-specs and ux-specs are peer co-informing tiers.

intent-specs

Prose-first description of capabilities and hard constraints, plus repo-wide defaults derived from intent. Always user-owned. defaults includes a structured Tech Stack section organized per DDD layer (Presentation, Application, Domain, Infrastructure) — empty fields signal "agent decides reasonably given other constraints"; filled fields are binding.

ArtifactPurposeItems
intentCapabilities, hard constraints, prose intentCAP, CST
defaultsRepo-wide rules + Tech Stack (per layer)DEF

product-specs ⇄ ux-specs (peer tiers)

Two co-informing tiers. Either can lead depending on mode (pm or ux). The approved derivation graph remains acyclic.

ArtifactPurposeItems
prdObjectives, requirements, NFRs, metricsOBJ, KR, FR, NFR
usmEpics, flows, stories, acceptance criteriaEPIC, FLOW, STORY, ACC
dmDomain model: ubiquitous language, bounded contexts, invariantsTERM, BC, AGG, INV
uxUser-visible surfaces, interactions, UX constraints, mockup referencesVIEW, INT, UXC, MOCK
ux-specs/mockups/Designer-supplied images, Figma snapshotsreferenced by MOCK

Mockups are first-class input evidence. In ux mode, mockups can directly drive product-spec generation via the generate-product-specs-from-ux task variant. Mockups don't become normative truth until their extracted obligations are represented as IDed contract items.

system-specs

System context, runtime topology, per-container component inventory, and per-component technical ownership. Each container carries a layer field (presentation / application / domain / infrastructure) that determines its rules and scope.

ArtifactPurposeItems
systemExternal actors, trust boundaries, system-wide NFRsEXT, TB, SNFR
containersRuntime/deployment topology and container inventoryCONT
containerOne runtime home and its component inventory; carries layerCMP
componentTerminal technical ownership boundaryIF, DEP, BEH

Layered architecture

The layer field on every container determines what it hosts and what rules apply. Stack choices declared in defaults (per layer) are inherited.

LayerHosts BCs?Components are…Notes
presentationNoUI components — pages, layouts, widgetsInherits Presentation stack. Typically one container; micro-frontends are minority.
applicationNoAPI surfaces, orchestration handlers, BFF endpointsOften one container per UI surface (web, mobile, admin); thin orchestration, not a "microservice" in the autonomous-capability sense.
domainYesService-shaped components hosting bounded contextsDecomposition is monolith (all BCs in one container) or multi-service (one container per BC = canonical microservices).
infrastructureNoNo internal components — declares consumed platform services as dependenciesDB, cache, queue, storage, compute platform.

Bounded contexts live exclusively in domain containers. The presentation and application layers have components but no BCs. The infrastructure layer declares dependencies, not internal components.

The contract graph

The graph is the parsed, queryable model of approved and draft artifacts. Nodes are IDed semantic items (entities); edges are typed derives_from relations. The graph is a DAG.

In v0.3, the contract graph is shaped as a knowledge graph: it stores the instantiated ontology — entities and their typed relations as they currently are. Provenance (decisions, generation events, eval findings, code-sync evidence, brownfield import history) lives in traces, designed to be sufficient for future graph promotion (see roadmap CGKG-B).

The graph answers:

  • What derives from what.
  • What is affected if a node changes.
  • Which artifacts own affected nodes.
  • What context to load for a scope.
  • What code-sync evidence claims realization.
  • What review or reconciliation packet to show.

This is what makes the methodology enforceable rather than aspirational.

Modes

A mode controls contract depth, approval gates, and UX surface.

ModeLeadUser-ownedAuto-advances
vibeSolointentsystem, code (compact stack — no graph, no code-sync)
pmProductintent, product, optionally uxsystem
devTechintent, systemproduct, optionally ux
uxDesignintent, ux, optionally productsystem; mockups can drive product-spec generation
expertArchitectall contract tiersnothing

Vibe → full upgrade is one-way. When a vibe project outgrows the compact stack, vibeloom init --upgrade --mode pm|dev|ux|expert promotes it. Existing code is import-analyzed against the freshly generated full contract.

Auto-advance is bounded. Even when delegated, a tier only auto-advances when structural eval passes and no semantic judgment requires escalation.

Operations

Orthogonal operations — none does another's job.

OperationWhat it does
initBootstrap an ungoverned repo with draft intent-specs.
importBootstrap from existing code; produces draft contract with confidence + evidence.
generateRegenerate affected/stale/uncovered downstream from approved upstream. Basis-idempotent.
evalRead-only validation. Produces findings; modifies nothing.
reviewInteractive findings loop on a single target. Fixes the target; doesn't propagate downward.
reconcileInteractive stale/drift loop with direction options (preserve contract / amend contract / user-defined).
approveAdvance a reviewed contract approval unit from draft to approved. Records an approval trace.
statusRead-only report; recommends next operation.

Lifecycle + traces

Two lifecycle states: draft and approved. draft means "not yet trusted as upstream truth"; approved means "downstream may derive from this." An approval unit is one contract tier — affected artifacts within it advance together.

On approval, the engine records a durable approval trace: the approved item identities plus a content fingerprint. This trace is what enables drift detection on subsequent passes.

Traces are organized into families:

  • approval — who/what approved which contract basis.
  • generation — what task generated what artifact from which basis.
  • eval — what checks ran and what findings resulted.
  • code-sync — how generated code maps back to the contract items it realizes.
  • decision — human-authored decision history, classified by record_type: IDR (intent-specs), PDR (product-specs), UDR (ux-specs), ADR (system-specs), or general (process / methodology / operational — doesn't change the contract). The load_bearing flag identifies the active subset still informing future generation.
  • import — evidence and confidence for brownfield inference.

Traces are durable provenance. They can propose improvements through mediated proposals, but cannot become contract truth without review and approval. Concrete schemas and storage: see Implementation · Traces.

Eval — the verification ladder

Eval operates on a ladder of decidable, mechanical, and heuristic tiers. Each tier is more rigorous than the next; the trajectory is to promote checks upward over time as the engine matures.

TierWhat it isToday (v0.3)Trajectory
Decidable Structural eval — deterministic checks the engine performs without an LLM. Lifecycle consistency, required fields, ID validity, reference integrity, DAG validity, coverage, dangling references, ownership rules, context sufficiency. Grows as new structural rules are codified (multi-source derives_from, BC/component topology, code-sync invariants).
Mechanical Validation runners — project-defined commands the orchestrator runs against generated artifacts. Declared in a project-level validation registry. Standard families: typecheck, lint, unit/integration tests, contract conformance, generated BDD, smoke/deploy. Grows as a runner library accumulates; some heuristic dimensions become mechanical when they can be expressed as runners.
Heuristic Semantic eval — agent-judged dimensions. Faithful representation, naming consistency, implicit dependencies, capability gaps, UX/product mismatch, mockup extraction gaps, target-platform mismatch. Shrinks over time as dimensions are promoted to mechanical or structural; the residue (genuine judgment-call cases) escalates to user.

The ladder is the honest answer to "what does semi-formal verification mean in v0.3?" — and the measurable trajectory: a future release ships when its decidable + mechanical share has grown.

Findings are categorized as blocking or advisory. Principle: false positives beat false negatives. Over-marking wastes work; under-marking lets incoherence leak past gates.

Drift and status

VibeLoom uses two parallel taxonomies — drift forms (causes) and status categories (item states) — to make incoherence locatable rather than aspirational.

Drift forms describe how mismatches arise: structural (upstream item changed since downstream synchronized), lifecycle (approved file edited outside the flow), semantic (downstream meaning shifted even when structure passes). Each form maps to a different detection mechanism in the engine.

Status categories describe item lifecycle states at any moment: current, stale, uncovered, dangling, drifted, obsolete. uncovered is distinct from stale — newly approved upstream creates downstream obligations that no downstream item can yet depend on.

Both taxonomies are VibeLoom-specific classifications, not derived from external literature. Other framings exist (Rath's semantic/coordination/behavioral for agent-to-agent drift; VentureBeat's "context decay" narrative for the silent-failure pattern). VibeLoom's framework is targeted specifically at contract-vs-code drift.

Detection mechanism + state diagrams: see Implementation · Approval traces and drift detection.

VibeLoom vs spec-driven tools

Spec-driven development was the right step. Contract-driven is the next.

Spec Kit, Kiro, and BMAD all elevated the load-bearing artifact above code — but kept it per-feature: each spec drives one cycle, then ships and goes static. Their durable layers (constitutions, steering files, persona checklists) are thin. VibeLoom keeps the contract load-bearing across the whole lifecycle: derivation, eval, drift detection, reconciliation, traceability across components.

Dimension VibeLoom GitHub Spec Kit Kiro BMAD
Where the complexity budget goes Contract graph + reconciliation Per-feature workflow + constitution IDE + per-feature spec pipeline Per-feature workflow + role personas (PM, Architect, Dev, QA)
Scope of governance Whole-system (graph) Per-feature + global constitution Per-feature + global steering files Per-feature + persona checklists
What persists across generations Specs evolve, graph-tracked Specs decay, branch-scoped Specs go static post-creation Specs go static; checklists persist
Coupling to current model capability Low — value grows with model quality Medium-high — ceremony scaffolds the model High — workflow keeps the model on rails Medium — heavyweight ceremony per feature
Cross-cutting coherence Native (graph + DDD invariants) Constitution only — features don't talk Steering files only — specs siloed Personas don't carry cross-feature state
Sidebar: Tessl. Tessl pivoted in early 2026 away from per-file spec-as-source toward per-skill context management. Different bet — managing what the agent knows, not what it writes. Same direction as VibeLoom, smaller scope (per-skill, not whole-system).

Where each tool wins. Spec Kit is the strongest open-source starting point with the largest community. Kiro is the cleanest auditable per-feature trail for regulated environments inside an IDE. BMAD is the strongest workflow-with-personas for teams who want explicit role separation per feature. VibeLoom is the only one with a whole-system, structured, graph-connected contract.

Roadmap

Shipping in v0.3: the contract stack with ux-specs as peer to product-specs; modes (vibe / pm / dev / ux / expert); the contract graph; drift detection across structural / lifecycle / semantic forms; status taxonomy; the verification ladder; durable trace records with canonical families; scoped subagent dispatch with wave assembly; brownfield import; the methodology + implementation specs.

v0.4+: richer reconciliation with bounded auto-fix proposals (still always user-confirmed); dry-run generation; a contract REPL; a contract debugger; a cross-project contract pattern library; trace-derived learning. See the v0.4+ roadmap for the full feature brainstorm.

v1.0 horizon: stable trace and graph interfaces; engine API as a versioned contract; named integrations beyond Claude Code and Codex.
