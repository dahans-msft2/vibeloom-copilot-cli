From spec-driven to contract-driven.

SDD has three flavors — Kiro, Spec Kit, BMAD. codæ is the next level.

Spec-driven development (SDD) correctly moved AI coding away from raw prompting. codæ pushes the same impulse further: the spec stack should become a durable, traceable, approval-gated contract that governs the lifecycle, not a one-off planning artifact. This whitepaper compares the three main SDD tools at the methodology level and positions codæ relative to them. Tessl and Pythagora appear as sidebars rather than main comparators.

§1 — Two familiesSpec-driven development, then contract-driven.

Spec-driven development has become a recognized family. AWS Kiro1 turns natural prompts into structured requirements (in EARS notation), design, and tasks, anchored in an IDE with steering files and lifecycle hooks. GitHub Spec Kit3 makes specifications executable through a constitution + spec/plan/tasks/implement workflow. BMAD Method5 organizes ideation through implementation around specialized agents (analyst, PM, architect, developer, UX) and adaptive workflows. All three address the same problem from different angles.

codæ pushes the same impulse further. A spec is not enough if it expires after one feature or only guides one generation cycle. The specification stack must become a contract: persistent, derivation-aware, approval-gated, traceable, and used across the lifecycle as both memory and eval surface. VibeLoom is one concrete instantiation of the codæ paradigm.

SDD asks: how do we make specs better inputs to generation? codæ asks: how do we make contracts the durable control surface of the lifecycle?

This piece compares the three SDD tools at the methodology level — what each treats as source of truth, who governs change, how drift is handled — and shows where codæ extends the family. Tessl and Pythagora are real participants in the broader landscape but not main SDD methodology comparators in May 2026 — see the sidebars in §9.

§2 — The SDD familyThree flavors of the same impulse.

AWS KiroIDE-anchored SDD.

Kiro is an agentic AI development environment — IDE plus CLI — built around three pillars: specs (per-feature triplets of requirements.md in EARS notation, design.md, tasks.md; bugfix.md for fixes), steering (persistent project/workspace knowledge in .kiro/steering/*.md with always/conditional/ manual/auto inclusion modes; AGENTS.md is supported), and hooks (event-driven agent prompts or shell commands that fire on file save, prompt submission, tool use, and spec task execution).1 2

The methodology bet underneath: developers will adopt spec discipline when it is embedded in the IDE workflow they already live in. Kiro's GA milestone added property-based testing for spec correctness, checkpointing, CLI surfaces, and team plans — extending the discipline toward more rigorous validation while keeping the IDE as the home base.

GitHub Spec KitConstitution + per-feature artifact bundle.

Spec Kit's official documentation defines spec-driven development as making specifications executable, directly generating working implementation rather than only guiding it.3 The core command flow is /speckit.constitution, /speckit.specify, /speckit.plan, /speckit.tasks, and /speckit.implement, with optional /speckit.clarify, /speckit.analyze, and /speckit.checklist to catch drift and ambiguity at the artifact layer before code is generated. Spec Kit supports integrations, extensions, presets, workflows, and project-local overrides.

The methodology bet underneath: a constitution plus per-feature executable specs and extensible process machinery can make AI generation more predictable. The structural gap is post-merge spec persistence — branch-scoped feature artifacts do not automatically compound into a system-level description, which becomes a real problem on mature codebases.

BMAD MethodAgent-role / workflow SDD.

BMAD describes itself as an AI-driven development framework spanning ideation and planning through agentic implementation.5 6 It provides specialized AI agents — Analyst, Product Manager, Architect, Developer, UX Designer, and others — and guided workflows that adapt to project complexity. BMad Builder allows creating custom agents, workflows, and modules. The framework is closer to codæ in spirit than the other SDD tools because it governs a broader development lifecycle rather than only single-feature workflow or per-file specs.

The methodology bet underneath: structured agent roles and adaptive workflows can make AI-assisted development behave more like a disciplined team process. The structural gap is graph and audit formalism — BMAD organizes humans and agents into roles and phases but does not (yet) materialize a first-class derivation graph or trace substrate.

§3 — codæ in the pictureContract-driven lifecycle governance.

codæ — instantiated by VibeLoom — turns the specification stack into a contract: persistent, IDed, derivation-aware, approval-gated, traceable, and used as both memory and eval surface. The artifact stack covers intent-specs, product-specs, peer ux-specs, system-specs, context, code, plus traces, review packets, reconciliation packets, and code-sync evidence.

The methodology bet underneath: long-lived AI-generated systems need a durable contract graph, not only better feature specs or workflow prompts. The contract is the artifact a human can comprehend; code is downstream. Agent Behavioral Contracts research7 provides supporting evidence that contract-style enforcement on agents produces measurable governance improvements (5.2–6.8 soft violations per session detected vs uncontracted baselines; 88–100% hard-constraint compliance across 1,980 sessions on 7 models) — not yet a proof of full lifecycle governance, but the right shape of mechanism.

codæ is an hommage to Bertrand Meyer's Design by Contract.8 The inheritance is the discipline of explicit obligations between software elements. The boundary moves upward — from routine/class contracts to system-generation contracts. The decidability gap is acknowledged honestly in the manifesto: today's contracts are checked semantically, not boolean. The trajectory is to push more of the contract toward decidability via structural eval and validation runners.

§5 — Cognitive surfaceHow big is the human-mendable surface?

The codæ manifesto's central claim is that the human-mendable surface should be measured in items, not lines of code. Each of the three SDD comparators answers what surface a human is supposed to hold differently:

  • Kiro — per-feature triplet (medium) plus steering files (small, persistent). Mixed-scale; the steering collection plays the role of standing knowledge that survives between features.
  • Spec Kit — small, persistent constitution plus a series of medium-sized per-feature artifact bundles. Mixed-scale; the global surface is what survives between features.
  • BMAD — phase-by-phase artifacts (PRD, architecture, UX, stories) accumulating across the project lifecycle. Larger total surface than the other two, organized by role rather than by graph.
  • codæ / VibeLoom — deliberate, structured stack whose total size scales with mode. vibe intentionally small (compact intent + flat system). expert is the full multi-tier stack — larger, but every tier covers a different abstraction so per-tier cognitive load is bounded.

The right question isn't "which is smaller." It's which sizes for the team and codebase. A team of two doesn't need an expert-mode stack. A multi-team product can't comprehend steering files alone. Cognitive surface is the dimension where each tool implicitly picks a target user — and where codæ's mode system explicitly tries to address more than one target inside one methodology.

§6 — Drift handlingWhat happens to coherence over time?

Drift is the question every spec-driven approach is built around, and the dimension where the four diverge most cleanly:

  • Kiro. Hooks fire on file events to cascade spec changes; property-based testing of specs is now part of GA. Steering files carry standing knowledge that outlasts a single feature. Post-completion spec lifetime is mostly convention.1 2
  • Spec Kit. Artifact-layer drift detection via /speckit.analyze and /speckit.checklist catches inconsistencies before code generation.3 4 The structural gap is post-merge: branch-scoped specs do not compound into system-level documentation, so drift between features is invisible at the spec layer.
  • BMAD. Workflow correction, "correct course," and readiness checks are built into the agent orchestration; phases re-plan when an upstream artifact changes.5 6 The framework does not yet materialize drift as a graph property or expose status categories at item granularity.
  • codæ. Drift forms detected explicitly: stale (downstream depended on changed approved truth), uncovered (approved upstream lacks required downstream realization), dangling (downstream references removed upstream), drifted (semantic mismatch or unflagged direct edit), obsolete (upstream basis superseded conceptually). Reconciliation is a first-class operation with a packet, not an emergent practice.

The honest 2026 caveat: there is no peer-reviewed benchmark comparing drift outcomes across these four tools. Each mechanism is well-described in current docs and practitioner reports; the empirical comparison the field needs hasn't been published yet.

§7 — The bet each makesWhat each is wagering survives.

Underneath every methodology choice is a structural bet about what's worth governing and what should evolve:

  • Kiro bets that an IDE-enforced phase workflow plus steering plus event-driven hooks gives developers the right governance at the right moments. Vindicated if developers want governance built into the tool they already live in.
  • Spec Kit bets that a constitution plus per-feature artifact bundles plus phase-gate analysis is enough governance. Vindicated if most teams' system-level coherence emerges from the constitution rather than from a system-level spec.
  • BMAD bets that structured agent roles plus adaptive workflows make AI-assisted development behave like a disciplined team process. Vindicated if the agent-role abstraction scales across project complexity without needing a graph or audit formalism.
  • codæ bets that a tiered, mutually-derived contract stack that survives the lifecycle is the only structural answer to drift at scale. Vindicated when, at the tail of a codebase's life — original team gone, multiple agents in parallel, architecture revised — the only artifact a human can still hold is the contract. (See the manifesto for the case.)

§8 — SDD maturity ladderWhere vibeloom fits.

The 2026 SDD taxonomy9 places existing approaches across three rigor levels:

  • Spec-first — specs guide initial development, then drift away from the code that ships.
  • Spec-anchored — specs and code co-evolve with explicit enforcement; the spec doesn't decay because something keeps checking it.
  • Spec-as-source — specs alone are edited; code is regenerated; humans never touch generated code.

codæ argues for a fourth level: contract-driven. The spec is not one source for one file or one feature; it is the multi-tier, mutually-derived, drift-detecting contract that governs the lifecycle. Same impulse as SDD; larger surface; deeper governance.

SDD maturity ladder, extended. Levels 1–3 are the rigor tiers in Piskala's 2026 taxonomy. Kiro, Spec Kit, and BMAD all sit at level 2 (different mechanisms — IDE hooks vs phase gates vs role workflows — same family). Tessl was at level 3 pre-pivot; the January 2026 shift to skills-as-package-manager makes its current placement uncertain (see §9). codæ argues for a fourth level — contract-driven — distinguished by lifecycle governance and graph-based drift detection.

§9 — SidebarsTessl and Pythagora.

Two tools are sometimes grouped with SDD but are not, in May 2026, the right comparators for a codæ methodology discussion:

TesslNow context/skills package management.

Tessl pivoted in January 2026 away from per-file spec-as-source toward "the package manager for agent skills."10 11 Current Tessl positions itself as a versioned registry of workflow-procedure skills, docs, rules, and other agent-context bundles ("tiles"), with evaluation, distribution, and lifecycle management for that context. That is better understood as skills/context infrastructure than as a feature-spec or contract-stack methodology. Tessl remains relevant because it proves the market is moving from one-off prompts toward evaluated, versioned agent context. codæ agrees with that direction but applies it to system-specific truth, not skill distribution.

PythagoraApp-generator / AI-developer lineage.

Pythagora describes itself as an AI teammate inside VS Code or Cursor powered by specialized agents that plan, code, review, test, debug, and deploy full-stack apps.12 GPT Pilot, its open-source lineage, is no longer maintained as the primary product and redirects to Pythagora.ai. Pythagora is relevant as app-generator / AI-developer companion lineage but is not the best methodology comparator for SDD vs codæ — the framing is closer to "AI does the coding work for you" than to "structured artifacts govern the system."
